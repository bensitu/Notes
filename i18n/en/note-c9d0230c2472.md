# Common naming principles and conventions :id=h-979954a42517

Choose class, method, and variable names according to their responsibilities, and keep team interfaces consistent during development.

**Prerequisites and versions:** Most naming rules are conventions, not language requirements. A prefix does not determine speed, return type, or whether a lookup succeeds. Follow the language, framework, and existing team conventions first.

**Using the examples:** Unless all files and execution steps are explicitly listed, code blocks are independent fragments for their sections. Complete omitted code and placeholder names. Lines marked as incorrect explain problems. Do not combine alternative implementations from one section.

Naming conventions keep code consistent, reduce communication costs, and help teams develop efficiently. A name should reveal the characteristics, meaning, or purpose of the code, so readers can quickly follow the program. The name should communicate the intent and match the actual behavior.

Clear names reduce comments that merely explain what the code does, but the reasons for complex rules, boundary conditions, and external constraints still need explanation. Do not remove necessary business context just to reduce comments.

## 1. Start with basic principles :id=h-1fa8a3f274d0

A good naming style lets readers understand a variable or function from its name. The name should match its purpose. We cannot comment on every line of code, so names should make the code explain itself instead of depending on comments.

### ① Use consistent coding conventions :id=h-aea901eea10c

When writing a submodule or derived class, follow the naming style of the base class or surrounding module. Keep conventions such as camel case and brace placement consistent throughout the module.

### ② Keep naming consistent :id=h-ba80a920873e

For example, use consistent prefixes such as is, can, or need for Boolean variables.

**A function name must match what the function actually does**

For example, a function named getXXX that also performs add and update operations makes troubleshooting difficult. Class, variable, and method names must describe their actual meaning and behavior.

Consult a dictionary and choose a familiar word that closely describes the purpose. Refer to JDK names, common vocabulary, and domain terms. Short names suit small scopes; larger scopes need more descriptive names.

Consider a Cache class with a function that checks whether a key has expired:

```java
public boolean isExpired(String key) {
        // See note 1 below.
    long curTimestamp = DateUtils.nowUnixTime();
    // See note 2 below.
    long storeTimestamp = getStoreTimestamp(key);
          if (curTimestamp - storeTimestamp > MAX_EXPIRE_SECONDS) {

                // See note 3 below.
                delete(key);

                return true;
    }
    return false;
}
```

Example notes:

1. Current timestamp
2. Get the timestamp when the key was stored
3. Notice that delete is a hidden side effect here.

The name suggests that this function only checks whether the key has expired. However, it also deletes an expired key. This mismatch between the name and behavior leaves a serious trap for later maintainers.

There are two ways to improve this code:

Option 1: remove the hidden behavior

```java
public boolean isExpired(String key) {
        // See note 1 below.
    long curTimestamp = DateUtils.nowUnixTime();
    // See note 2 below.
    long storeTimestamp = getStoreTimestamp(key);
        if (curTimestamp - storeTimestamp > MAX_EXPIRE_SECONDS) {
                return true;
    }
    return false;
}
```

Example notes:

1. Current timestamp
2. Get the timestamp when the key was stored

Option 2: rename the function

```java
public int deleteIfExpired(String key) {
        // See note 1 below.
    long curTimestamp = DateUtils.nowUnixTime();
    // See note 2 below.
    long storeTimestamp = getStoreTimestamp(key);
          if (curTimestamp - storeTimestamp > MAX_EXPIRE_SECONDS) {
                return delete(key);
    }
    return 0;
}
```

Example notes:

1. Current timestamp
2. Get the timestamp when the key was stored

### ③ Form names from a verb and a noun :id=h-a12ce9cd6969

1. Use English words that are clear, pronounceable, and accurately express the intent. Correct spelling and grammar make names easier to understand and reduce ambiguity.

2. Avoid arbitrary abbreviations that readers cannot recognize. Shortening Function to Fu, for example, makes code much harder to read.

3. Use combinations of complete words for custom programming elements so that the code explains itself.
   A good example is AtomicReferenceFieldUpdater in the JDK, which atomically updates a volatile field holding an object reference.

4. Do not reject a useful name merely because it is long

Meaning comes first: a reasonable method name need not be rejected for being long. However, an excessively long name can indicate that the method does too much. Consider splitting it, following the single-responsibility principle.

Once the meaning is clear, keep the name concise by removing unnecessary words or using recognizable abbreviations. Examples follow:

1. ActivityRuleRepository.findActivityRuleById() can become ActivityRuleRepository.findById(), because the Repository interface already establishes that it queries activity rules.

2. The example shortens void updateRuleForRevision(String ruleString) to void updateRule4Revision(String ruleStr).

3. Following the style of toString, ActivityRule convert2ActivityRule(String ruleStr) can be shortened to ActivityRule toActivityRule(String ruleStr).

### ④ Keep names short and informative :id=h-ea49982d27e3

Use as few words as possible while still describing the purpose. For example, staff is shorter and easier to remember than a combination of company, person, and collection.

Common abbreviations such as msg, idx, cnt, btn, id, and flg can also be used. If an abbreviation is not widely understood, agree on it with teammates and explain its meaning in a comment.

As a readability guideline, keeping variable and function names around 4–18 characters can help readers understand the code.

Overlong variables: howLongDoesItTakeToOpenTheDoor, howBigIsTheMaterial, …

Concise variables: timeToOpenTheDoor, materialSize.

### ⑤ Avoid overly similar names, puns, and ambiguity :id=h-0fa092042c3b

Do not distinguish similar identifiers only by letter case, such as i versus I or function versus Function.

Name identifiers with opposite meanings consistently.

Use appropriate antonym pairs for opposing meanings, for example:

| Opposite meanings     |                      |                  |
| --------------------- | -------------------- | ---------------- |
| add / remove          | begin / end          | create / destroy |
| insert / delete       | first / last         | get / set        |
| increment / decrement | put / get            | cut / paste      |
| add / delete          | lock / unlock        | open / close     |
| min / max             | old / new            | start / stop     |
| next / previous       | source / target      | show / hide      |
| send / receive        | source / destination | up / down        |

These pairs help readers understand related variables and functions.

Avoid numeric suffixes such as value1 and value2, **unless the logic genuinely requires numbering**.

### ⑥ Use fewer type prefixes :id=h-46fe2f5a87b7

A name should reveal its meaning and preferably suggest its type. A descriptive suffix is also acceptable.

Avoid using broad words such as data, info, or value on their own.

### ⑦ Do not use get for every method :id=h-29190aeebca2

Describe actions with more precise verbs: request, acquire, search/lookfor/find, inquire, build, or create. Use an action-specific name such as doGet when performing an operation such as a query.

Typical get and set accessors form a pair and have lightweight implementations.

The performance of get, find, and query depends on the implementation and data-access method, not the prefix. For JavaBean properties, keep standard get/set names so frameworks can recognize them.

1. Finding data: find / lookFor looks for matching data. Define the return behavior when no match exists.
2. Searching data: search; the data being sought may not exist.
3. query emphasizes the query operation, while find emphasizes the intent to locate something. The interface contract determines the return type: either can return an entity, DTO, collection, or Optional. The name alone does not determine the type.

## 3. Naming methods :id=h-20004fe9573b

1. Unlike class names, method names usually use verbs or verb phrases. Together with the parameters or their names, they describe a verb–object action. A good function name tells readers what the function does.

2. Prefer concrete names over abstract ones. For checking whether a server port can begin listening, CanListenOnPort() is clearer than ServiceCanStart().

3. Meaning comes first: a reasonable method name need not be rejected for being long. However, an excessively long name can indicate that the method does too much. Consider splitting it, following the single-responsibility principle.

   Once the meaning is clear, keep the name concise by removing unnecessary words or using recognizable abbreviations. Examples follow:

   1. UserDao.findUserById() can become UserDao.findById(), because the DAO interface already establishes that it queries users.
   2. The example shortens void updateUserForName(String name) to void updateForName(String name).
   3. Following the style of toString, the example shortens User convertToUserModel(String uid) to ttoUserModel(String ruleStr).

4. Words such as add, insert, and append have related meanings. Choose precisely and consistently; for example, use append rather than add for joining strings.

Spring's method names provide another example:

1. getBean: a lightweight entry point that calls doGetBean.

   ```java
   public Object getBean(String name) throws BeansException {
     return this.doGetBean(name, (Class)null, (Object)null, false);
   }
   ```

2. doGetBean: checks the cache first and calls createBean to create a bean if it is absent.

   ```java
   String beanName = this.transformedBeanName(name);
   Object sharedInstance = this.getSingleton(beanName);
   this.createBean(beanName, mbd, args);
   ```

3. createBean: validates the bean and then calls doCreateBean to create it.

4. doCreateBean: performs the actual bean creation.

### ① Method conventions for Service / DAO layers :id=h-9bd2e757433d

1. Use the prefix get when retrieving one object.

2. Use list and a plural ending for multiple objects, for example listObjects.

3. Use count for methods that return a count.

4. Use save / insert for insertion methods.

5. Use remove / delete for deletion methods.

6. Use update for modification methods.

7. Retrieving data: fetch

8. Finding data: find looks for matching data; its name does not guarantee that a match exists.

9. Searching data: search; the data being sought may not exist.

10. query emphasizes the query operation, while find emphasizes the intent to locate something. The interface contract determines the return type: either can return an entity, DTO, collection, or Optional. The name alone does not determine the type.

## 4. Naming variables :id=h-8abfdc00229a

### **Principle 1: nouns, noun combinations, or adjectives** :id=h-12be50882dfb

Variables usually describe an object or one of its properties, so nouns, noun combinations, or adjectives generally make their meaning easier to understand.

### **Principle 2: use consistent vocabulary** :id=h-254143616ad6

Use consistent vocabulary within a project or scenario. For example, total and sum can both express a total; choose one and use it consistently wherever that meaning is intended.

1. For constants and variables, place the noun indicating the type at the end to make the name easier to recognize.

> Examples following this convention: startTime / workQueue / nameList / TERMINATED_THREAD_COUNT
> Examples rejected by this convention: startedAt / QueueOfWork / listName / COUNT_TERMINATED_THREAD

Using result for a return value inside a method can clarify its flow, for example userListResult.

2. \[Required by this convention] Do not prefix Boolean fields in a POJO with is. Some frameworks can interpret such names differently and cause serialization errors.

   > **Explanation:** The first table-naming convention in the MySQL rules uses is_xxx for yes/no columns. Therefore, configure a mapping from is_xxx to xxx in <resultMap>.
   >
   > **Example to avoid:** A primitive boolean field named isDeleted has a method isDeleted(). When the framework derives the property name from the method, it treats the property as deleted. That does not match the intended field name, so property lookup can fail with an exception.
3. Name constants in uppercase with underscores between words. Make their meaning complete and clear, even when that requires a longer name.
4. End collection names with a type or a plural s

Java has collection types such as List, Map, and Set. There are two common ways to name collection variables:

- Use a plural ending in s

```java
 List<Student> students = new ArrayList<>();
```

- Use the collection type as a suffix

```java
 List<Student> studentList = new ArrayList<>();
```

Both approaches are valid; choose according to the context. The first is shorter. The second distinguishes related collections more clearly when several types appear in the same local scope. For example:

```java
List<Student> studentList = new ArrayList<>();
Map<Long, Student> studentMap = Maps.newHashMap();
for (Student stu : studentList) {
  studentMap.put(stu.getId(), stu);
}
```

Suggested approach:

- If the local scope contains only one collection type, prefer a plural name.
- If several related collection types occur locally, prefer a type suffix.
