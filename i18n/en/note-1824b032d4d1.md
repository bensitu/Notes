# Backend automated testing: verify behavior and failure paths :id=h-75905a7a5a16

Learning objectives: understand what unit, integration, and end-to-end tests protect, and run meaningful checks before committing.

**Scope:** The running Java project uses JUnit Jupiter, MockMvc, and Spring Security Test managed by the Spring Boot 4 BOM. It retains org.junit.jupiter API and does not mix old JUnit 4 annotations.

## Test layers :id=h-e705fe7ea735

| Level                      | What is verified                                           | Main cost                                   |
| -------------------------- | ---------------------------------------------------------- | ------------------------------------------- |
| Unit tests                 | Inputs and outputs of one business rule                    | Very low; dependencies are usually isolated |
| Web tests                  | Routing, binding, validation, statuses, and security rules | Require a Web test environment              |
| Database integration tests | SQL, mapping, transactions, and constraints                | Require a database                          |
| End-to-end tests           | The full path from real login to page operations           | Slower; diagnosis crosses components        |

Assertions should express business results. Checking only that a method was called or “the program did not throw” is usually insufficient to protect critical behavior.

## Minimal run instructions :id=h-f93d522c75e4

```powershell
Set-Location examples/taskboard/backend
mvn -B -ntp verify
```

See [TaskApiTest.java](examples/taskboard/backend/src/test/java/example/tasks/TaskApiTest.java) for complete tests; reports are in target/surefire-reports. On failure, inspect the first assertion and root cause rather than guessing from Maven's final error line.

## What this example actually covers :id=h-ff913d3d8512

- Anonymous task reads return 401.
- Authenticated writes without CSRF return 403.
- Blank titles return 400.
- Task creation returns 201 and Location.
- Repeated writes with the same old version return 409.
- Ordinary roles cannot delete; administrators can.
- Reading after deletion returns 404.

Mocking an identity does not mock the whole security system; filters still participate. Browser tests separately verify password login, cookies, and token refresh.

## Test data and transactions :id=h-22c399716ab6

The test class uses @Transactional to roll back database changes made by same-thread MockMvc requests after each test. With real-port requests, the server runs in another thread, so the test thread's transaction does not automatically roll back the server's work.

Each test creates its own data without depending on execution order, fixed auto-increment keys, or leftovers. Time, randomness, and external APIs need controllable inputs for repeatable failure reproduction.

Design separate cases for missing and duplicate values, boundary lengths, authorization denial, missing resources, and concurrent updates. Do not pack every scenario into one giant test that makes failures hard to locate.

## Real databases and Testcontainers :id=h-3eb360170f30

Default tests use H2 for speed, but do not cover MySQL dialects, lock scope, or MongoDB / Redis / RabbitMQ behavior.

After installing Docker, Testcontainers can create isolated real database instances for tests. Extensions must select Boot 4-compatible dependencies and define connection lifecycle, migrations, and cleanup, rather than only replacing the JDBC URL.

The repository also provides an MySQL run path with Docker Compose. Minimal verification starts real services, applies migrations, repeats the same read/write and conflict cases, then uses two independent connections to test lock waits.

## Common errors and development quick reference :id=h-be365f4e9286

| Error                                              | Consequence                                   | Improvement                                           |
| -------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------- |
| Old JUnit 4 annotations with a Jupiter engine      | Tests may not run or lifecycle hooks may fail | Unify imports and engine                              |
| Skip all assertions when an external service fails | CI is green without verification              | Fail explicitly or label integration tests separately |
| Multiple tests share fixed records                 | Fails when order changes                      | Each test owns its data                               |
| Assert only HTTP 200                               | May miss incorrect content and state          | Check semantics, response, and data results together  |
| Copy implementation details into tests             | Many irrelevant failures during refactoring   | Check observable behavior                             |

In CI, ensure test failures block later releases. Do not obtain green results by ignoring exit codes or skipping tests by default.
