## 1. SSM integration :id=h-a9c992ac6492

We have studied the three frameworks `Mybatis`, `Spring`, and `SpringMVC`. Today's main topic is integrating them to develop business features. Let's learn how, step by step.

### 1.1 Process analysis :id=h-fff9713e4894

(1) Create the project

- Create a Maven web project
- Add the jar dependencies required for SSM to pom.xml
- Write the web project's entry configuration class, implement `AbstractAnnotationConfigDispatcherServletInitializer`, and override the following methods:
  - getRootConfigClasses(): returns the Spring configuration class → requires the ==SpringConfig== configuration class
  - getServletConfigClasses(): returns the SpringMVC configuration class → requires the ==SpringMvcConfig== configuration class
  - getServletMappings(): sets the request mapping rules for SpringMVC
  - getServletFilters(): configures filters to resolve Chinese character encoding issues in POST requests

(2) SSM integration \[==focus on writing each configuration==]

- SpringConfig
  - Mark the class as a configuration class: @Configuration
  - Scan the Service package: @ComponentScan
  - Manage transaction in the Service layer: @EnableTransactionManagement
  - Read an external properties configuration file: @PropertySource
  - Import Mybatis configuration classes for Mybatis integration: @Import
    - Third-party data source configuration class: JdbcConfig
      - Build a DataSource data source, DruidDataSouroce, injecting the four database connection parameters: @Bean @Value
      - Build a platform transaction manager, DataSourceTransactionManager: @Bean
    - Mybatis configuration class: MybatisConfig
      - Build SqlSessionFactoryBean and set alias scanning and the data source: @Bean
      - Build MapperScannerConfigurer and configure package scanning for the DAO layer
- SpringMvcConfig
  - Mark the class as a configuration class: @Configuration
  - Scan the Controller package: @ComponentScan
  - Enable SpringMVC annotation support: @EnableWebMvc

(3) Feature modules \[depend on the specific business module]

- Create database tables
- Create corresponding model classes from the database tables
- Implement database CRUD through the Dao layer (interfaces + automatic proxies)
- Write the Service layer \[Service interfaces + implementation classes]
  - @Service
  - @Transactional
  - Integrate Junit to unit-test the business layer
    - @RunWith
    - @ContextConfiguration
    - @Test
- Write the Controller layer
  - Receive requests: @RequestMapping @GetMapping @PostMapping @PutMapping @DeleteMapping
  - Receive data: simple types, POJO, nested POJO, collections, arrays, and JSON types
    - @RequestParam
    - @PathVariable
    - @RequestBody
  - Delegate to the business layer
    - @Autowired
  - Return results
    - @ResponseBody

**Explanation:**

- Injecting bookDao into the Service shows a red underline. Why?

  - BookDao is an interface without an implementation class. Since an interface cannot be instantiated, the injected object should ultimately be a proxy.
  - Spring's IOC container creates and manages the proxy.
  - The IOC container is created only when the web server starts.
  - When IDEA checks dependencies, it finds no suitable class to inject, so it reports an error.
  - At runtime, however, the proxy is created and the framework injects it using DI, so execution is unaffected.

- How can this be resolved?

  - Ignore it, since the application runs normally

  - Adjust the error highlighting severity

## 2. Consistent result wrapping :id=h-e88f8292aa59

### 2.1 Defining the data transfer protocol between the presentation layer and frontend :id=h-74c6574503c2

After SSM integration and feature development, let's analyze the remaining problems in the example. The first problem is:

- Controller add, update, and delete methods return boolean data to the frontend.

  ![1630653359533](Resources/1630653359533.png)

- A Controller single-record query returns an object.

  ![1630653385377](Resources/1630653385377.png)

- A Controller all-record query returns a collection object.

  ![1630653468887](Resources/1630653468887.png)

We already return three data types to the frontend, and this number will grow with business requirements. Parsing different results becomes confusing for frontend developers. If the backend returns a consistent result structure, the frontend can parse all responses in the same way, simplifying development.

Can we make the returned data consistent? The basic idea is:

- To wrap the returned data: ==create a result model class and place the data in its data property==
- To indicate the operation and whether it succeeded: ==place the operation result in the code property==
- To return error information after failure: ==place the specific message in the message (msg) property==

![1630654293972](Resources/1630654293972.png)

Based on this analysis, define a consistent result class.

```java
public class Result{
    private Object data;
    private Integer code;
    private String msg;
}
```

\*\*Note:\*\* The name Result and its fields are not fixed. Add or remove them as needed and provide constructors for convenient use.

##### Step 2: Define the Code class for return codes :id=h-91ec2ff811c3

```java
// See note 1 below.
public class Code {
    public static final Integer SAVE_OK = 20011;
    public static final Integer DELETE_OK = 20021;
    public static final Integer UPDATE_OK = 20031;
    public static final Integer GET_OK = 20041;

    public static final Integer SAVE_ERR = 20010;
    public static final Integer DELETE_ERR = 20020;
    public static final Integer UPDATE_ERR = 20030;
    public static final Integer GET_ERR = 20040;
}

```

Example notes:

1. Status codes

Values such as 20011 and 50001 are business identifiers in the response body, not HTTP status codes. Later exception examples explicitly set HTTP 400 and 500. In real APIs, return 404 for a missing resource and consider 201 for successful creation. An empty list still means a successful query. Axios routes non-2xx responses to catch by default, so handle both network and business errors.

\*\*Note:\*\* Constants in Code are also flexible. Add or remove them as needed, such as splitting query results into GET_OK, GET_ALL_OK, GET_PAGE_OK, and so on.

##### Step 3: Modify Controller return values :id=h-93ed9d0938fc

```java
// See note 1 below.
@RestController
@RequestMapping("/books")
public class BookController {

    @Autowired
    private BookService bookService;

    @PostMapping
    public Result save(@RequestBody Book book) {
        boolean flag = bookService.save(book);
        return new Result(flag ? Code.SAVE_OK:Code.SAVE_ERR,flag);
    }

    @PutMapping
    public Result update(@RequestBody Book book) {
        boolean flag = bookService.update(book);
        return new Result(flag ? Code.UPDATE_OK:Code.UPDATE_ERR,flag);
    }

    @DeleteMapping("/{id}")
    public Result delete(@PathVariable Integer id) {
        boolean flag = bookService.delete(id);
        return new Result(flag ? Code.DELETE_OK:Code.DELETE_ERR,flag);
    }

    @GetMapping("/{id}")
    public Result getById(@PathVariable Integer id) {
        Book book = bookService.getById(id);
        Integer code = book != null ? Code.GET_OK : Code.GET_ERR;
        String msg = book != null ? "" : "数据查询失败，请重试！";
        return new Result(code,book,msg);
    }

    @GetMapping
    public Result getAll() {
        List<Book> bookList = bookService.getAll();
        Integer code = bookList != null ? Code.GET_OK : Code.GET_ERR;
        String msg = bookList != null ? "" : "数据查询失败，请重试！";
        return new Result(code,bookList,msg);
    }
}
```

Example notes:

1. Use a consistent return value for every controller method

### 3.3 Project exception handling approach :id=h-df13c927174f

#### 3.3.1 Exception classification :id=h-4ba1e28045a9

Now that we can use exception handlers, how should we handle exceptions in our project?

There are many exception types. Writing an @ExceptionHandler method for each one would require many handlers, so classify exceptions first:

- Business exceptions (BusinessException)

  - An operation cannot be completed within the normal business process

    - User input does not follow the required format, such as a string in an age field

      ![1630659599983](Resources/1630659599983.png)

  - Exceptions caused by improper user actions

    - For example, a user deliberately submits incorrect data

      ![1630659622958](Resources/1630659622958.png)

- System exceptions (SystemException)

  - Exceptions that are foreseeable but unavoidable during execution
    - For example, a database or server outage

- Other exceptions (Exception)

  - Exceptions the programmer did not anticipate, such as a missing file

    ![1630659690341](Resources/1630659690341.png)

After classifying exceptions, provide a specific solution for each type:

#### 3.3.2 Exception handling solutions :id=h-60e7de99dcb1

- Business exceptions (BusinessException)
  - Send an appropriate message to the user, asking them to follow the required operation
    - Common examples include “Username already exists” and “Incorrect password format.”
- System exceptions (SystemException)
  - Send a fixed message to reassure the user
    - The system is busy. Please try again later.
    - The system is undergoing maintenance and upgrades. Please try again later.
    - The system has encountered a problem. Please contact the system administrator.
  - Send a specific notification to operations staff, requesting maintenance
    - Use SMS, email, or the company's internal messaging software
  - Record logs
    - Notifications and logging are invisible to users; they are backend operations.
- Other exceptions (Exception)
  - Send a fixed message to reassure the user
  - Send a specific notification to developers, requesting a fix and future handling of the case
    - Usually caused by an overlooked case, such as missing null validation
  - Record logs

### 5.1 Interceptor concepts :id=h-89d1bf1dee84

Before explaining interceptors, look at the following diagram:

![1630676280170](Resources/1630676280170.png)

(1) A browser request first reaches the Tomcat web server.

(2) Tomcat determines whether the request targets a static or dynamic resource.

(3) Static resources are accessed directly in Tomcat's project deployment directory.

(4) Dynamic resources must be handled by the project's backend code.

(5) Before finding the specific method, configured filters (possibly several) execute in order.

(6) Processing then enters the central dispatcher (part of SpringMVC); SpringMVC intercepts requests according to configured rules.

(7) Matching requests are processed: the corresponding controller method runs and returns a result.

(8) Requests that do not match the rules are not processed.

(9) How can we add logic before and after every Controller method?

That is what interceptors do.

- An Interceptor dynamically intercepts method calls; in SpringMVC, it intercepts controller method execution.
- Purpose:
  - Execute predefined code before and after specified method calls
  - Prevent the original method from executing
  - Summary: Interceptors add behavior around existing processing.

You may notice that:

- Interceptors and filters are similar in purpose and execution order.

This raises a question: How do interceptors differ from filters?

- Different ownership: Filter belongs to Servlet technology; Interceptor belongs to SpringMVC.
- Different targets: Filter enhances all access, while Interceptor enhances only SpringMVC access.

### 5.3 Interceptor parameters :id=h-428ef15e9e61

#### 5.3.1 Preprocessing method :id=h-93bca170325b

Runs before the original method: preHandle

```java
public boolean preHandle(HttpServletRequest request,
                         HttpServletResponse response,
                         Object handler) throws Exception {
    System.out.println("preHandle");
    return true;
}
```

- request: request object
- response: response object
- handler: the current handler object. For annotated controllers it is usually HandlerMethod; handlers for static resources and other cases may have different types. Check the type before casting.

The request object provides request data, such as the `Content-Type` request header.

```java
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
    String contentType = request.getHeader("Content-Type");
    System.out.println("preHandle..."+contentType);
    return true;
}
```

The handler parameter provides information about the method.

```java
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
    HandlerMethod hm = (HandlerMethod)handler;
    String methodName = hm.getMethod().getName();// See note 1 below.
    System.out.println("preHandle..."+methodName);
    return true;
}
```

Example notes:

1. Get the method name

#### 5.3.2 Postprocessing method :id=h-4ef4f8585e28

Runs after the original method; does not run if the original method was blocked.

```java
public void postHandle(HttpServletRequest request,
                       HttpServletResponse response,
                       Object handler,
                       ModelAndView modelAndView) throws Exception {
    System.out.println("postHandle");
}
```

The first three parameters are the same as above.

modelAndView: If handler execution produces a result, read and adjust its data and page information.

Since we currently return json data, this parameter is rarely used.

#### 5.3.3 Completion method :id=h-dbf5bd70d8dd

Called after the request completes, but only for interceptors whose preHandle returned true successfully. If an interceptor returns false, its own afterCompletion is not called; earlier interceptors that allowed processing still receive their completion callbacks.

```java
public void afterCompletion(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler,
                            Exception ex) throws Exception {
    System.out.println("afterCompletion");
}
```

The first three parameters are the same as above.

ex: If an exception occurs during handler execution, it can be handled separately here.

Since we already have a global exception handler, this parameter is also rarely used.

Of these methods, ==preHandle== is used most often. Its return value decides whether processing continues. Put business logic here: return true if the conditions are met, or false to block processing otherwise.

Step 3: Run the application and observe the order

![1630680435269](Resources/1630680435269.png)

Execution order depends on configuration order: as in the earlier example of operations staff entering the server room, the first in is the last out.

- Multiple interceptors form an interceptor chain.
- The chain runs according to the order in which interceptors were added.
- If an interceptor blocks the original handler, all subsequent interceptors stop running.
- When interceptor processing is interrupted, only afterCompletion of previously configured interceptors runs.

![1630680579735](Resources/1630680579735.png)

preHandle: Runs in configuration order; later interceptors do not run if an earlier one returns false or throws an exception.

postHandle: Runs in reverse configuration order and may not run.

afterCompletion: Runs in reverse configuration order and may not run.

If this order is hard to remember, keep one principle in mind: ==use the actual execution result as your guide.==
