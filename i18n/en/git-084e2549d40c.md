## Understand four locations first :id=h-feb6894e5658

The working tree is the files on disk; the index is content prepared for the next commit; local commits are existing history; the remote is the repository on a collaboration server. Saving does not automatically stage files, and committing does not automatically push.

| Command              | What it shows or changes                                                           |
| -------------------- | ---------------------------------------------------------------------------------- |
| git status           | Show working tree, index, and branch status                                        |
| git diff             | Show unstaged changes                                                              |
| git diff --cached    | Show changes prepared for commit                                                   |
| git log --oneline -5 | Show recent commits                                                                |
| git fetch origin     | Update remote-tracking information without automatically changing the working tree |

## Minimal exercise: edit documentation and commit :id=h-5cb4e82cd692

Start at the repository root. If uncommitted changes exist, identify which belong to this task instead of staging everything directly.

```powershell
git status
git fetch origin
git switch main
git pull --ff-only
git switch -c feature/update-taskboard-guide
```

After editing this project's documentation, stage only the target file:

```powershell
git diff -- examples/taskboard/README.md
git add -- examples/taskboard/README.md
git diff --cached --check
git diff --cached
git commit -m "docs: clarify taskboard startup"
git push -u origin feature/update-taskboard-guide
```

This file is an exercise target; do not manufacture meaningless changes just to practice. Explain the reason for each commit in one sentence. After pushing, open a Pull Request for peer review.

## Handling conflicts :id=h-1f1db562390a

A conflict means Git cannot automatically decide how to combine two changes, not that choosing either side is necessarily correct.

1. Run git status to identify conflicted files.
2. Read both changes' intentions, edit the final content, and remove conflict markers.
3. Check that adjacent paragraphs, links, and examples remain consistent.
4. Stage resolved files; commit for a merge, or run git rebase --continue for a rebase.
5. If you cannot continue, use git merge --abort or git rebase --abort as appropriate for the current operation.

Do not casually rewrite shared-branch commits. Only your own unpublished branches are suitable for tidying commits according to team agreements. Coordinate before updating published branches and understand the scope of --force-with-lease checks.

## Undo quick reference :id=h-566ec5b93851

| Situation                               | Action                                                                     | Caution                                                            |
| --------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Wrong file staged                       | git restore --staged -- filename                                           | Unstages while retaining working-tree content                      |
| Last local commit omitted a file        | Stage the missing file, then git commit --amend                            | Changes the commit ID; do not use to casually alter shared history |
| A published commit introduced a problem | git revert commit-ID                                                       | Create a reversing commit, then inspect and test                   |
| Want to discard working-tree changes    | Inspect the diff first, then decide whether to run git restore -- filename | Overwrites uncommitted content in that file                        |

Do not treat reset --hard or force-pushing as universal fixes. After a mistake, stop further history rewriting and inspect git reflog. Uncommitted, unbacked-up data is not guaranteed recoverable.

## Verification and common errors :id=h-0f0de8d28707

Check the staged diff before committing and git show --stat HEAD afterward. After pushing, fetch and compare local and remote branches. “Working tree clean” does not mean “already pushed.”

Before merging, run at least the tests and build relevant to the change. Update prose and examples together. Do not commit passwords, .env, database files, node_modules, or build directories.

Commit lockfiles together with new dependencies. Ignore rules only prevent new files from being tracked; they do not automatically remove committed secrets from history. Revoke leaked credentials and handle history according to team procedures.
