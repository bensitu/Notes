**JSF (JavaServer Faces)** is a server-side component-based user interface framework for developing web applications. It provides a well-defined programming model with rich APIs and tag libraries. This article covers JSF 2.x, using Facelets as the default view technology. JSF was later renamed Jakarta Faces; the javax examples here cannot be used directly as Faces 3/4 code. It is written in Java.

The JSF API provides components (`inputText`, `commandButton`, and others) and helps manage their state. It also provides server-side validation, data conversion, page navigation definitions, extensibility, internationalization support, accessibility, and more.

The JSF tag library adds components to web pages and connects them to objects on the server. It also includes tag handlers that implement the component tags.

These features and tools let you create server-side user interfaces more clearly.

**Facelets technology**

Facelets is an open-source web templating system. It is the default view handler technology for JavaServer Faces (JSF). It requires valid input XML documents to work correctly. Facelets supports all JSF UI components and focuses entirely on building views for JSF applications.

**AJAX support**

JSF provides built-in AJAX support, so you can submit application requests to the server without refreshing the web page. JSF also supports partial rendering using AJAX.

## 1. JSF lifecycle :id=h-c6340313e8e2

The lifecycle is the sequence of processing a Faces request from its arrival at the server until a response is generated. A page is represented by a component tree, such as a form containing input fields and buttons. The component tree is a server-side object structure, not the browser's DOM.

A normal postback (submitting the same Faces form) usually goes through the following six phases. Opening a page for the first time usually involves mainly Restore View and Render Response; it does not validate input through the form-submission process.

| Phase                   | What it does                                                                                 | Details beginners should remember                                                                                              |
| ----------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1. Restore View         | Creates a new view or restores the original view from saved state                            | FacesContext belongs to the current request; it is not the same context object retained indefinitely from the previous request |
| 2. Apply Request Values | Reads submitted values from request parameters and stores them in components                 | The values are usually still strings at this point; this does not mean they have been written to the Bean                      |
| 3. Process Validations  | Converts data types and validates input                                                      | Displays messages when conversion or validation fails, usually skipping model updates and business methods                     |
| 4. Update Model Values  | Writes valid component values to Bean properties                                             | Requires writable properties, such as properties with corresponding setters                                                    |
| 5. Invoke Application   | Runs action methods of components such as buttons and handles navigation                     | Business methods run after input passes conversion and validation                                                              |
| 6. Render Response      | Generates HTML or a partial-update response from the component tree and saves the view state | The page displays messages using h:message / h:messages                                                                        |

The execute phase collectively refers to the first five phases; the render phase is the sixth phase. Render Response must not be counted as two separate processing phases.

### Early termination and partial requests :id=h-ca37c86818bb

- Calling `FacesContext.getCurrentInstance().renderResponse()` skips to Render Response after the current phase finishes. It does not skip rendering.
- Calling `responseComplete()` indicates that the application has already handled the response, for example by completing a redirect; Faces stops generating its usual page response.
- Setting `immediate="true"` on an input component moves its conversion and validation to Apply Request Values; immediate on a command component causes action events to be processed earlier. Do not confuse these effects or use immediate to bypass business validation.
- Ajax execute specifies which components participate in processing, and render specifies which components to update. Do not assume that input excluded from execute has been updated in the Bean.

Rendering a view does not recompile the entire Java application or immediately destroy every Bean. A Bean's lifetime is determined by its scope; Faces saves view state on the client or server according to configuration. Do not include sensitive data in page output or rely on client-side state to keep it secret.

## 2. JSF managed Beans :id=h-09b76029a54b

A managed bean is a plain Java class containing a set of properties and `getter` and `setter` methods.

Managed bean methods commonly perform the following functions:

- Validating component data
- Handling events triggered by components
- Processing logic to determine the application's next navigation destination
- It can also serve as the model in the JSF framework.

**JSF managed Bean example**

Look at the following example code:

```java
public class User {
    private String name;
    public String getName() {
        return name;
    }
    public void setName(String name) {
        this.name = name;
    }
}
```

You can use this `bean` in the following ways.

- By configuring it in an XML file.
- By using annotations.

### 1. Configuring managed Beans through an XML file :id=h-bff8b4d5b1f9

The following code shows how to register a JSF managed bean:

```xml
<managed-bean>
    <managed-bean-name>user</managed-bean-name>
    <managed-bean-class>User</managed-bean-class>
    <managed-bean-scope>session</managed-bean-scope>
</managed-bean>
<managed-bean>
  <managed-bean-name>message</managed-bean-name>
  <managed-bean-class>com.yiibai.test.Message</managed-bean-class>
  <managed-bean-scope>request</managed-bean-scope>
</managed-bean>
```

Configuring a `bean` in an xml file is an older approach. With this approach, create an xml file named `faces-config.xml`; JSF provides tags for configuring the `bean`.

In the example above, we specify `bean-name`, `bean-class`, and `bean-scope`, making the bean accessible in the project.

### 2. Configuring managed Beans with annotations :id=h-bfeea3e9e9f6

The following code shows how to register a JSF managed bean using annotations:

```java
import javax.faces.bean.ManagedBean;
import javax.faces.bean.ManagedProperty;
import javax.faces.bean.RequestScoped;
import java.io.Serializable;

@ManagedBean(name = "user")  // Using ManagedBean annotation
@RequestScoped                             // Using Scope annotation
public class User implements Serializable {
      private static final long serialVersionUID = 1L;

    private String name;
    public String getName() {
        return name;
    }
    public void setName(String name) {
         this.name = name;
    }

      @ManagedProperty(value="#{message}")   // Uing another bean
       private Message message;

      public void setMessage(Message message) {
    this.message = message;
  }
}
```

@ManagedBean registers a JSF managed Bean. If name is omitted, the first letter of the simple class name is usually made lowercase; for example, User becomes user. eager=true means creation at startup only with ApplicationScoped; other scopes, including request and session, still create Beans as needed.

Message above is an example dependency: define and register a Bean named message yourself, with a scope no shorter than that of the injection target. The name in setMessage must match the message property. JSF 2.3 already recommends CDI, and Faces 4 removed the legacy ManagedBean; use this set of javax.faces.bean annotations only when maintaining older projects.

This is an alternative to the application configuration resource file approach and reduces the work of configuring managed beans.

The `@RequestScoped` annotation specifies the managed scope. Annotations define the scope in which a bean is stored. If no scope is specified, the bean defaults to request scope (RequestScoped).

You can use the following scopes on bean classes:

- **Application (\[@ApplicationScoped])**: Application scope is shared by all users. The bean is created on the first HTTP request, or at web application startup when `eager = true` is set in `@ManagedBean`, and is destroyed when the web application shuts down.
- **Session (\[@SessionScoped])**: Session scope survives multiple HTTP requests in the web application. It is created on the first HTTP request and destroyed when the HTTP session becomes invalid.
- **View (\[@ViewScoped])**: Created when the user interacts with a single page (view) of the web application, and destroyed when the user navigates to another view.
- **Request (\[@RequestScoped])**: Created for an HTTP request in the web application and destroyed when the HTTP response associated with that HTTP request completes.
- **None (\[@NoneScoped])**: Indicates that no scope is defined for the application. Created when EL is evaluated and destroyed after EL evaluation.
- **Custom (\[@CustomScoped]**: A nonstandard, user-defined scope. Its value must be configured as `java.util.Map`. Custom scopes are rarely used.

**@ManagedProperty annotation**

JSF is a simple static dependency injection (DI) framework. The @ManagedProperty annotation marks a managed bean property for injection of another managed Bean.

### 3. Eagerly managed Beans :id=h-0b4fd06ec113

Managed `bean`s are lazy by default. This means a bean is instantiated only when requested by the application.

To force a `bean` to be instantiated early, you can instantiate the `bean` at application startup and place it in application (`@ApplicationScoped`) scope. Set the managed bean's `eager` property to `true`, as shown below:

```java
@ManagedBean(eager=true)
```

# JSF user interface components :id=h-4f883595d365

The JSF HTML tag library represents HTML form components and other basic HTML elements for displaying data or accepting user input. The JSF form sends this data to the server when submitted.

To use these tags, add the following URI namespace to the html node.

```html
<html
   xmlns="http://www.w3.org/1999/xhtml"
   xmlns:h="http://java.sun.com/jsf/html"
>
```

The following table lists the user interface components.

| Tag                       | Function                                                                          | Rendered as                                                                                | Appearance                                                                  |

2. Creating a managed Bean

User.java

```java
import javax.faces.bean.ManagedBean;
import javax.faces.bean.RequestScoped;

@ManagedBean(name = "user")
@RequestScoped
public class User {
    private String name;
    private String email;
    private String password;
    private String gender;
    private String address;

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public String getPassword() { return password; }
    public void setPassword(String password) { this.password = password; }
    public String getGender() { return gender; }
    public void setGender(String gender) { this.gender = gender; }
    public String getAddress() { return address; }
    public void setAddress(String address) { this.address = address; }
}
```

This example demonstrates only form binding and page navigation within the same request. It does not write users to a database and is not a complete registration feature. Do not echo passwords on a page; real registration requires server-side validation and dedicated password-hash storage. No redirect is used here, so request-scoped properties remain accessible on the response page.

# JSF web resources :id=h-0a1f5141f722

JSF web resources are the resources needed for correct rendering in a web application. They include images, script (JS) files, and any user-created component libraries.

JSF provides a standard way to store web resources. You can use either of the following storage locations.

- Store them in a subdirectory of the resources directory at the web application root: `resources/resource-identifier`, for example `resources/js`, `resources/css`, and so on.
- Resources packaged on a web application's classpath must be in a subdirectory of `META-INF/resources`: `META-INF/resources/resource-identifier`. You can use this structure to package resources in JAR files bundled with the web application.

At runtime, JSF (JavaServer Faces) searches for resources in the directory locations listed above, in that order.

Our application has the following structure.

```
root:project
|--.gitignore
|--.iml
|--pom.xml
|--README.md
|--doc:文档
```

## Accessing image files :id=h-e95b26874d4d

JSF provides the `<h:graphicImage />` tag to access image files in a web application. In the following example, first create the resources directory and a subfolder named `images`. After creating the folders, write the following code.

The `<h:graphicImage>` tag specifies that the image named `hello.gif` is in `resources/images` (relative to the web application root).

```html
<h:body>
<h:form id="user-form" enctype="multipart/form-data">
<h:graphicImage value="#{resource['images:hello.gif']}"/>
<h:graphicImage library="images" name="hello.gif"/>
</h:form>
</h:body>
```

This code accesses the image in two ways: first, using the resource array in Expression Language; second, by specifying the library attribute.

## Accessing CSS files :id=h-774b472c63c7

The `<h:outputStylesheet>` tag accesses CSS resources in a web application. Create a subdirectory inside the resources folder.

The following example accesses the `test.css` file from a web page. The code for *index.xhtml* is shown below:

```html
<html xmlns="http://www.w3.org/1999/xhtml"
xmlns:h="http://xmlns.jcp.org/jsf/html">
<h:head>
<title>Web Resources Example</title>
<h:outputStylesheet library="css" name="test.css"/>
</h:head>
<h:body>
<h1>Welcome to The Yiibai JSF!</h1>
</h:body>
</html>
```

The code for the file *test.css* is shown below:

```css
h1 {
color: red;
text-align: center;
}
```

## Accessing JavaScript files :id=h-00b6258d1850

The `<h:outputScript>` tag accesses JavaScript files in a web application.
