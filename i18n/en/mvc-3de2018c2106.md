## The three responsibilities in MVC :id=h-549c1e38412c

MVC stands for Model, View, and Controller.

| Part       | Responsibility                                                  | Common example                           |
| ---------- | --------------------------------------------------------------- | ---------------------------------------- |
| Model      | Represents business data and business-processing capabilities   | User objects and order services          |
| View       | Displays data and provides a user interface                     | HTML, Thymeleaf templates, and Vue pages |
| Controller | Receives requests, calls business logic, and prepares responses | Spring MVC controllers                   |

**Mapper is not the M in MVC, and Controller is not View.** MVC describes responsibilities, not three fixed Java packages.

## MVC and three-layer architecture :id=h-9fc33017ea40

Java web backends commonly separate presentation, business logic, and data access. MVC describes how a view, controller, and model cooperate; it does not map one-to-one onto these three layers.

```text
Browser -> Controller -> Service -> DAO / Mapper -> Database
Browser <- Controller <- Service <- DAO / Mapper <- Database
```

- Controller: receives paths, parameters, and request bodies; validates input; calls a Service; and returns a page or data.
- Service: implements business rules and coordinates transactions. For example, placing an order affects both inventory and orders.
- DAO / Mapper: accesses the database, for example to query users or update inventory.

Dependencies normally point downward: Controller depends on Service, and Service depends on DAO. Lower layers should not call back into higher layers. A higher layer can depend on an interface and receive an implementation through injection.

## Common object names :id=h-9b32368c66eb

| Name             | Meaning                                        | Usage                                                                                                                 |
| ---------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| POJO             | Plain Old Java Object: an ordinary Java object | Does not require a particular framework; getter/setter are not mandatory, and persistence-related use is not excluded |
| Entity / PO / DO | Object representing persistent data            | Often corresponds to table fields, but not every system requires one class per table                                  |
| DTO              | Data Transfer Object                           | Passes data across interfaces or layers and includes only fields the caller needs                                     |
| VO               | View Object                                    | Organizes fields for a page or API response                                                                           |
| DAO              | Data Access Object                             | Encapsulates methods that access the database                                                                         |
| Domain           | Domain model                                   | Expresses business concepts and rules, rather than merely combining several tables into a large object                |

Teams use these names differently. Agree on the purpose before standardizing names. For example, a database user record includes a password hash, while a user list only needs an ID and nickname. Returning a UserView avoids exposing sensitive fields to the frontend.

## Passing data between layers :id=h-6a2bc214a250

```text
JSON request -> CreateUserRequest -> Service -> UserEntity -> Database
JSON response <- UserView <- Service <- UserEntity <- Database
```

A simple query can return a DTO directly. Complex business logic can introduce domain objects. Add VO, DTO, and DO according to their responsibilities; every request does not need six object types and four conversions.

## Example directory layout :id=h-9556033567c4

```text
src/main/java/com/example/app/
  controller/
  service/
  repository/
  entity/
  dto/
  config/
src/main/resources/
  mapper/
  static/
  templates/
```

Use lowercase Java package names. The repository package holds DAO or Mapper interfaces; the mapper resource directory holds SQL mapping files.

In Spring Boot, static holds static assets and templates holds template-engine files. Adding Thymeleaf does not automatically replace every static page. JSP uses a different deployment model; putting it in templates alone does not make it render.

## Service and interface boundaries :id=h-608381cd367f

Keep Controllers concise, but they handle more than validation and conversion: presentation responsibilities include HTTP status codes and response headers.

A Service handles business logic. Not every table needs complete CRUD, and not every Service needs a ServiceImpl. Introduce interfaces when needed for replaceable implementations, test boundaries, or team conventions.

Split complex business logic into cooperating services and inject them through constructors. Do not expose internal structures through chains such as getXXXService().getRepository().

| Operation    | Example method name     | Behavior to define                             |
| ------------ | ----------------------- | ---------------------------------------------- |
| Create       | createUser(request)     | Validation and duplicate-data handling         |
| Update       | updateUser(id, request) | What happens when the target does not exist?   |
| Query one    | findUserById(id)        | Return Optional or null, or throw an exception |
| Query a list | listUsers(query)        | Filtering, sorting, and pagination             |
| Delete       | deleteUser(id)          | Whether a missing target is an error           |

An aggregate in DDD models a business-consistency boundary; it is not another name for a Service that contains many child Services.
