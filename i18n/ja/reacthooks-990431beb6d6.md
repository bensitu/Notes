## Hookの呼び出し規則 :id=h-b121d883c3c0

通常のHookは関数コンポーネントやカスタムHookのトップレベルで呼び出し、各レンダリングで呼び出し順序を保ちます。条件分岐、ループ、通常のユーティリティ関数、イベントハンドラー内でuseState / useEffectを呼び出さないでください。

Reactのuse APIには独自の規則があり、その例外をすべてのHookに適用することはできません。カスタムHookが再利用するのはロジックであり、すべての呼び出し元が同じstateを自動的に共有するわけではありません。

<a id="section-2"></a>

## よく使うツールの早見表 :id=h-e98150157855

| ツール                   | 適した用途                    | 該当しない用途                      |
| --------------------- | ------------------------ | ---------------------------- |
| useState              | 単純なローカル状態                | 現在のクロージャーの変数を即座に変更する代入       |
| useReducer            | 複数のアクションによる一連の状態の更新      | HTTPリクエストを実行する場所             |
| useEffect             | 外部システムとの同期の開始、更新、クリーンアップ | すべての計算やクリック処理の標準的な格納場所       |
| useRef                | DOM参照や表示を駆動しない可変値の保持     | ページ更新の通知                     |
| Context               | コンポーネントツリーで共通の依存関係を渡す    | 自動的に高性能になる万能の状態ストア           |
| useMemo / useCallback | 必要に応じた計算結果や関数の同一性の保持     | 業務処理の正しさの保証                  |
| useTransition         | 後回しにできるレンダリング更新の指定       | リクエストのキャンセル、レート制限、データベースのロック |

まず状態の管理元を明確にし、ロジックを正しくします。その後、測定して計算のキャッシュが必要か判断してください。「最適化」のためにすべての式をuseMemoで包まないでください。

<a id="section-3"></a>

## Effectとイベントを分ける :id=h-91b402851a5e

ユーザーがクリックしてタスクを作成するときは、イベント内でPOSTを送信します。Effectは購読、タイマー、外部状態の読み取り、コンポーネントの表示に結び付いた同期に適しています。既存のstateから直接計算できる値を、Effectで別のstateに書き込む必要は通常ありません。

Effectの依存関係は実際に使用するリアクティブな値から決まります。警告を消すために依存配列の要素を削除しないでください。クロージャーはあるレンダリングの値を保持するため、依存関係が不足するとリスナーが古いデータを読み続ける可能性があります。

<a id="section-4"></a>

## 実行可能なサンプルのリクエストのクリーンアップ :id=h-742f0ceb1bef

[TaskPage.tsx](examples/react-taskboard/src/TaskPage.tsx)は最初にタスクを読み込むときにAbortControllerを作成し、activeフラグで古いコールバックも拒否します。

```tsx
useEffect(() => {
  const controller = new AbortController();
  let active = true;
  loadTasks(controller.signal).then(items => {
    if (active) setTasks(items);
  }).catch(error => {
    if (active) setError(error instanceof Error ? error.message : '读取失败');
  });
  return () => {
    active = false;
    controller.abort();
  };
}, []);
```

これはコンポーネント内部の抜粋です。useEffect、loadTasks、setterを適切にインポートまたは宣言してください。完全版では認証と処理中の状態も扱います。

読み取りのキャンセルは、すでに送信した業務操作をサーバーが取り消したことを意味しません。検索条件やルートパラメーターが変わるたびに古いリクエストをクリーンアップし、古い応答が新しい結果を上書きしないようにします。

<a id="section-5"></a>

## StrictModeと繰り返し実行 :id=h-839a65ef240d

開発環境のStrictModeは、追加のレンダリング検証やEffectのsetup / cleanupサイクルなどを実行し、不純なレンダリングやクリーンアップの不足を検出します。これを根拠に、本番環境のEffectが必ず1回しか実行されないとは言えません。

「実行済み」refですべての検証を回避したり、重複リクエストを隠すためにStrictModeを削除したりしないでください。書き込み操作は明示的なイベントに置き、購読、タイマー、読み取りはクリーンアップできるようにします。

サンプルのpending refは、同じイベント処理への再入を同期的に防ぐフラグです。busy stateは待機状態の表示に使用します。ボタンの無効化だけでは、ページ間やユーザー間の業務処理の冪等性は保証されません。

## 状態が増えたときの構成 :id=h-bc0ebd3e69c0

まず状態を共通の親に引き上げます。複雑な状態遷移には純粋なreducerを検討し、アクションで何が起きたかを表します。Contextでreducerの結果とdispatchを渡せますが、providerの値が変わると、それに依存するconsumerに影響します。

リモートデータとローカルのUI状態は分けて考えます。キャッシュ、有効期限、再試行、重複リクエストの統合は適切なデータツールに任せられます。導入前に読み込みキー、キャンセル、権限の境界を明確にし、サーバーデータをすべて複数のグローバルストアにコピーしないでください。

SSR環境では、ユーザーの状態をモジュールのトップレベルの可変シングルトンに保存しないでください。Nodeプロセスは複数のユーザーを処理します。リクエスト間の状態分離についてはSSRのドキュメントを参照してください。

## 検証とよくある問題 :id=h-056a2dab967f

サンプルでnpm testとnpm run buildを実行します。続いて開発者ツールで、ページ切り替え、素早い操作、リクエスト失敗、ログイン期限切れの際に、入力が保持され、ボタンが復帰し、古いデータによる更新が防がれるか確認します。

| 問題                    | よくある原因                                          |
| --------------------- | ----------------------------------------------- |
| Effectがリクエストを繰り返す     | 依存関係に毎回新規作成されるオブジェクトがあり、Effectが関連するstateを更新している |
| タイマーが重複して実行される        | cleanupの不足                                      |
| refが変わってもページが更新されない   | refはレンダリングを引き起こさない                              |
| reducerで副作用が重複することがある | reducer内でリクエストや外部データの変更を実行している                  |
| 2回のクリックで業務処理が2件発生する   | フロントエンドのフラグはサーバー側の冪等性制約の代わりにはならない               |
