## キャッシュは主データベースの代わりではない :id=h-0e07c090c4cf

キャッシュは再取得できるデータを保存し、繰り返しのアクセスコストを減らします。まず遅い箇所を測定してから、何をキャッシュするかを決めます。キャッシュは無効化、権限の分離、障害処理を複雑にします。

| 概念       | 意味                                        |
| -------- | ----------------------------------------- |
| ヒット / ミス | キャッシュが見つかった / 信頼できるデータソースから読み取る必要がある      |
| TTL      | 有効期限。期限切れの古い値を有効なキャッシュとして扱い続けてはいけない       |
| エビクション   | メモリが上限に達した後、方針に従ってデータを削除すること              |
| 永続化      | Redisがデータを保存する仕組みであり、業務データベースのバックアップとは異なる |
| ホットスポット  | 多数のリクエストが少数のキーに集中すること                     |

## 最小限の実行手順 :id=h-d90e8a470430

まず一貫したサンプルプロジェクトのディレクトリでRedisを起動します。

```powershell
docker compose --env-file .env --profile tools up -d redis
```

別のターミナルでPythonプロジェクトへ移動し、.envと同じパスワードを使用します。

```powershell
Set-Location examples/taskboard/python
uv sync --locked --all-extras
$env:REDIS_PASSWORD = 'local_redis_change_me'
uv run --locked python -m task_tools.cache_demo
```

[完全なコード](examples/taskboard/python/src/task_tools/cache_demo.py)は60秒間有効なJSONキャッシュを設定し、結果を読み、TTLを観察し、最後に自身のデモキーを削除します。実行時にはRedisが接続を受け付けている必要があります。初回起動時は先にサービスログを確認してください。

ここで使うnotes:task:v1:demoは練習用の名前空間で、Redis全体を走査したり消去したりしません。サンプルは独立したコマンドであり、JavaのタスクAPIを自動的にキャッシュしません。

## Cache-asideの順序と競合 :id=h-cab0f1c7d66a

一般的な読み取りは、キャッシュを読み、ミスしたらデータベースを読み、結果をキャッシュしてTTLを設定します。変更時は先にデータベースをコミットし、その後関連キャッシュを削除します。

この順序でも競合は起こり得ます。別の古いクエリが、削除後に古いデータをキャッシュへ書き戻す場合があります。TTLは古い値の存続時間を制限しますが、強い整合性は保証しません。重要なデータには、バージョン検証、制御された更新、権威あるストレージからの直接読み取りを検討します。

「遅延二重削除」ですべての整合性問題が解決すると断言しないでください。許容する古さ、障害時の復旧方法、複数インスタンスの協調方法を明確にする必要があります。

<a id="section-4"></a>

## 有効期限、容量、キャッシュの一斉失効 :id=h-004eff3afa00

SETのex引数は値とTTLを同時に設定し、値の書き込み後にプロセスが終了して有効期限を設定し忘れることを防ぎます。TTLに小さなランダムのずれを加えると、多数のキーの同時失効を避けられます。

ホットキーの失効時は、リクエストの統合、制御された更新、制限付きの排他制御でデータベースへのアクセスを減らせますが、待機時間と失敗時の方針を明確にする必要があります。存在しないデータをキャッシュするときは適切に短いTTLを設定し、後で追加されたデータが速やかに見えるようにします。

maxmemoryとエビクション方針は用途に合わせて設定します。Redisに失えないタスクと失ってよいキャッシュを同時に保存する場合、すべてのキーを削除し得る方針を安易に採用してはいけません。

<a id="section-5"></a>

## ロックと障害の境界 :id=h-aeab07e1c5ce

SET key token NX PX durationは、期限付きの排他制御の出発点にできます。解放時は所有者のtokenを比較し、原子的に削除しなければなりません。GETの後にDELを行う方法は競合があり、安全なロック解放ではありません。

リースの期限切れ後も古い保持者が実行を続ける場合があります。重要な書き込みには下流側のバージョンやfencingによる保護が必要です。Redisのロックは、データベースの一意制約やトランザクションの代わりにはなりません。

接続と読み書きにタイムアウトを設定します。キャッシュ障害時にデータベースへフォールバックできるかは、データベース容量、レート制限、業務の正しさを踏まえて判断し、無制限にアクセスを戻してはいけません。

## 検証と開発の早見表 :id=h-b377a7febe45

| 練習                | 観察事項                               |
| ----------------- | ---------------------------------- |
| 書き込み後に読み戻す        | JSONのフィールドとTTLが適切であること             |
| TTLを待ってから読み取る     | キャッシュミスとなり、値がないことを空タスクの取得成功として扱わない |
| Redisを停止する        | タイムアウトに上限があり、エラーを特定できる             |
| 期限切れキーへの大量の同時アクセス | データベースの負荷が急増しないか                   |
| タスク変更後に再び読み取る     | 許容された古い値の期間内に更新されるか                |

ユーザーAの結果をユーザーBへ返さないよう、キャッシュキーには必要なテナント、ユーザー、バージョンの要素を含めます。本番Redisをインターネットに直接公開せず、認証、ネットワーク、バックアップ、メモリ監視を合わせて設定します。
