# よく使う命名の原則と規約 :id=h-979954a42517

役割に合わせてクラス、メソッド、変数に名前を付け、チーム内のインターフェースに一貫性を持たせます。

**前提知識とバージョン：** 命名の多くは慣例であり、言語が強制する規則ではありません。接頭辞によって速度、戻り値の型、検索の成否は決まりません。まず言語、フレームワーク、既存のチーム規約に従ってください。

**サンプルの使い方：** 全ファイルと実行手順を明示したものを除き、コードブロックは節ごとの独立した断片です。省略部分や仮の名前を補ってください。誤りと示した行は問題の説明用です。同じ節の代替実装を混ぜないでください。

命名規約は、コードを統一し、意思疎通の負担を減らし、チームの開発を円滑にするためのものです。名前からコードの特徴、意味、用途が分かれば、読み手はプログラムの流れを理解しやすくなります。意図が伝わり、実際の動作と一致する名前にしましょう。

分かりやすい名前を使うと、「このコードが何をするか」だけを説明するコメントを減らせます。ただし、複雑な規則の理由、境界条件、外部の制約は引き続き説明が必要です。コメントを減らすために、必要な業務上の背景まで削除しないでください。

例を見てみましょう。

下の複雑なコメントの代わりに、その内容を名前で表す関数を作ります。

```javascript
// See note 1 below.
if ((employee.flags & HOURLY_FLAG) && (employee.age > 65)) {
  grantFullBenefits(employee);
}
```

例の説明：

1. 従業員が福利厚生をすべて受けられる条件を満たすか確認します。

次のように置き換えます。

```javascript
// See note 1 below.
if (employee.isEligibleForFullBenefits()) {
  grantFullBenefits(employee);
}
```

例の説明：

1. 従業員が福利厚生をすべて受けられる条件を満たすか確認します。

## 1. 基本原則を守る :id=h-1fa8a3f274d0

よい命名では、変数名や関数名を見れば用途を理解でき、名前と実態が一致します。すべてのコードにコメントを書くことはできないため、コメントに頼らず、名前からコードの意味が分かるようにします。

### ① コーディング規約を統一する :id=h-aea901eea10c

サブモジュールや派生クラスを書くときは、基底クラスやモジュール全体の命名スタイルに従います。キャメルケースや波かっこの位置など、モジュール内で規約を統一してください。

### ② 命名に一貫性を持たせる :id=h-ba80a920873e

例えば Boolean 型の変数では、is、can、need などの接頭辞を一貫して使います。

**関数名と実際の動作を食い違わせない**

例えば getXXX という関数の中で add や update まで行うと、原因の調査が難しくなります。クラス名、変数名、メソッド名は、実際の意味や動作と一致させてください。

辞書を調べ、用途に近く、分かりやすい単語を選びましょう。JDK の命名、一般的な語、業界の用語も参考になります。狭いスコープでは短い名前、広いスコープではより詳しい名前を使います。

例えば Cache クラスに、key の有効期限が切れているかを調べる関数があるとします。

```java
public boolean isExpired(String key) {
        // See note 1 below.
    long curTimestamp = DateUtils.nowUnixTime();
    // See note 2 below.
    long storeTimestamp = getStoreTimestamp(key);
          if (curTimestamp - storeTimestamp > MAX_EXPIRE_SECONDS) {

                // See note 3 below.
                delete(key);

                return true;
    }
    return false;
}
```

例の説明：

1. 現在のタイムスタンプ
2. key を保存した時点のタイムスタンプを取得する
3. ここでは delete が隠れた副作用になっている点に注意してください。

関数名からは key の有効期限を調べるだけに見えますが、実際には期限切れの key を削除しています。このような名前と動作の食い違いは、後から保守する開発者が問題を起こす原因になります。

改善方法は 2 つあります。

方法 1：隠れた処理を取り除く

```java
public boolean isExpired(String key) {
        // See note 1 below.
    long curTimestamp = DateUtils.nowUnixTime();
    // See note 2 below.
    long storeTimestamp = getStoreTimestamp(key);
        if (curTimestamp - storeTimestamp > MAX_EXPIRE_SECONDS) {
                return true;
    }
    return false;
}
```

例の説明：

1. 現在のタイムスタンプ
2. key を保存した時点のタイムスタンプを取得する

方法 2：関数名を変える

```java
public int deleteIfExpired(String key) {
        // See note 1 below.
    long curTimestamp = DateUtils.nowUnixTime();
    // See note 2 below.
    long storeTimestamp = getStoreTimestamp(key);
          if (curTimestamp - storeTimestamp > MAX_EXPIRE_SECONDS) {
                return delete(key);
    }
    return 0;
}
```

例の説明：

1. 現在のタイムスタンプ
2. key を保存した時点のタイムスタンプを取得する

### ③ 動詞と名詞を組み合わせる :id=h-a12ce9cd6969

1. 意図が伝わり、発音できる、適切な英単語を使います。正しいつづりと文法は、読み手の理解を助け、曖昧さを減らします。

2. 意味を推測できない独自の省略は避けてください。例えば Function を Fu と略すと、コードが非常に読みにくくなります。

3. 独自に定義するプログラム要素は、完全な単語を組み合わせて命名し、コード自体から意味が分かるようにします。
   例えば JDK の AtomicReferenceFieldUpdater は、オブジェクト参照を保持する volatile フィールドをアトミックに更新するクラスです。

4. 適切な名前なら、長さだけを理由に避けない

まず意味が伝わることを優先し、適切なメソッド名なら長さだけを心配する必要はありません。ただし、長すぎる名前は、そのメソッドの責務が多すぎる兆候でもあります。単一責任の原則を意識し、分割できないか検討してください。

意味が伝わることを前提に、不要な単語を省いたり、理解される省略形を使ったりして簡潔にします。次の例を見てください。

1. ActivityRuleRepository.findActivityRuleById() は ActivityRuleRepository.findById() に短縮できます。Repository インターフェースという文脈から、アクティビティールールを検索することが既に分かるためです。

2. この例では、void updateRuleForRevision(String ruleString) を void updateRule4Revision(String ruleStr) に短縮しています。

3. toString の形式を参考にすると、ActivityRule convert2ActivityRule(String ruleStr) は ActivityRule toActivityRule(String ruleStr) に短縮できます。

### ④ 短さと情報量を両立させる :id=h-ea49982d27e3

用途を十分に説明できる範囲で、できるだけ少ない語を使います。例えば staff は、company、person、collection を組み合わせた名前より簡潔で覚えやすい語です。

msg、idx、cnt、btn、id、flg など、広く通じる省略形も使えます。一般的でない省略形は、チーム内で合意し、コメントで意味を説明してください。

読みやすさの目安として、変数名や関数名を 4～18 文字程度に収めると、コードを理解しやすくなります。

長すぎる変数名：howLongDoesItTakeToOpenTheDoor、howBigIsTheMaterial など。

簡潔な変数名：timeToOpenTheDoor、materialSize。

### ⑤ 似すぎた名前や言葉遊びを避け、曖昧さをなくす :id=h-0fa092042c3b

i と I、function と Function のように、大文字と小文字だけで似た識別子を区別しないでください。

反対の意味を持つ識別子は、対応が分かる名前にします。

反対の意味には、適切な反意語の組を使います。例：

| 反対の意味                 |                      |                  |
| --------------------- | -------------------- | ---------------- |
| add / remove          | begin / end          | create / destroy |
| insert / delete       | first / last         | get / set        |
| increment / decrement | put / get            | cut / paste      |
| add / delete          | lock / unlock        | open / close     |
| min / max             | old / new            | start / stop     |
| next / previous       | source / target      | show / hide      |
| send / receive        | source / destination | up / down        |

こうした組み合わせにより、対応する変数や関数の意味を理解しやすくなります。

value1、value2 のような番号付きの名前は、**処理上、本当に番号が必要な場合**を除いて避けます。

### ⑥ 型を表す接頭辞を多用しない :id=h-46fe2f5a87b7

名前から意味が分かり、できれば型も推測できるようにします。説明的な接尾辞を付けてもかまいません。

data、info、value のように意味の広い語を、単独で使うことはなるべく避けます。

### ⑦ すべてのメソッドに get を付けない :id=h-29190aeebca2

動作をより正確な動詞で表します。例えば要求には request、取得には acquire、探索には search/lookfor/find、問い合わせには inquire、組み立てには build、作成には create を使います。検索などの処理を実行する名前には、doGet のような動作を表す語を使います。

一般的な get と set のアクセサーは対で用い、単純な処理にします。

get、find、query の性能は、実装とデータへのアクセス方法によって決まり、接頭辞では判断できません。JavaBean のプロパティーでは、フレームワークが認識できるよう、標準の get/set 命名を保ちます。

1. データを探す：find / lookFor は一致するデータを探します。見つからなかった場合の戻り値や動作を決めておいてください。
2. データを検索する：search。探しているデータが存在するとは限りません。
3. query は問い合わせの処理を、find は探す意図を強調します。戻り値の型はインターフェースの契約で決まり、どちらもエンティティー、DTO、コレクション、Optional を返せます。名前だけで型が決まるわけではありません。

## 2. クラスの命名規約 :id=h-e93f364749b6

1. クラス名は通常、名詞で終わり、データの保持と機能の提供のどちらを主な役割とするかが分かる名前にします。例えば ObjectBuilder なら、主に Object インスタンスを作るクラスだと推測できます。
2. この規約では、動詞に -er/or を付けたクラス名なら、その動詞で始まるメソッドを少なくとも 1 つ用意します。例えば ObjectBuilder には build- で始まるメソッドを置きます。これにより、クラスの役割を理解しやすくなります。

| 接頭辞                    | 意味    | 例               |
| ---------------------- | ----- | --------------- |
| Abstract または Base で始める | 抽象クラス | BaseUserService |

| 接尾辞        | 意味                                                    | 例                          |
| ---------- | ----------------------------------------------------- | -------------------------- |
| Controller | 外部に公開するインターフェースクラス                                    | UserController             |
| Service    | ほかのクラスへ業務上のサービスを提供するメソッドを持つサービスクラス                    | UserService                |
| Impl       | インターフェースではなく実装クラス                                     | UserServiceImpl            |
| Manager    | 汎用的な業務処理層                                             | UserManager                |
| Ixxx       | インターフェース                                              | IUserDao                   |
| Dao        | データアクセスのメソッドをまとめたクラス                                  | OrderDao                   |
| Listener   | イベントに応答するクラス                                          | PaymentSuccessListener     |
| Event      | イベントを表すクラス                                            | PaymentSuccessEvent        |
| Factory    | 特定のオブジェクトを生成するファクトリーを作るクラス                            | PaymentOrderFactory        |
| Adapter    | それまで対応していなかったオブジェクトを接続するためのクラス                        | DatabaseLogAdapter         |
| Job        | 時刻や間隔に従って実行するタスク                                      | PaymentOrderCancelJob      |
| Wrapper    | 別のクラスに足りない機能を追加するラッパークラス                              | SelectableOrderListWrapper |
| DO         | データベースのオブジェクトに対応するプロパティーを定義する（ORM：オブジェクトリレーショナルマッピング） | UserDO                     |
| DTO        | DTO：データ転送オブジェクト                                       | UserDTO                    |
| VO         | 表示層で使い、フロントエンド（APP / WAP / PC）に表示するためのもの              | UserVO                     |
| Entity     | エンティティ                                                | User                       |

> POJO は DO / DTO / BO / VO の総称です。クラス名を xxxPOJO にしないでください。

| 属性               | 制約                                                  | 例                                                    |
| ---------------- | --------------------------------------------------- | ---------------------------------------------------- |
| デザインパターンに関係するクラス | Builder、Factory など                                  | デザインパターンを使う場合は、ThreadFactory のように、対応するパターン名を接尾辞にします。 |
| Util クラス         | 通常は状態を持たず、static メソッドだけを持ちます。利用時にインスタンスを作る必要はありません。 | toStringUtil                                         |
| Helper クラス       | メンバーフィールドで状態を保持でき、通常はインスタンスを作ってから使います。              |                                                      |

- インターフェースの管理：XXXManager
- スレッド関連：XXXExecutor
- 初期化関連：XXXInitializer
- 処理関連：XXXHandler
- リスナー：XXXListener

## 3. メソッドの命名規約 :id=h-20004fe9573b

1. クラス名とは異なり、メソッド名は通常、動詞や動詞句を使います。パラメーターやその名前と組み合わせて、「動詞＋対象」の動作を表します。よい関数名なら、名前からその機能が分かります。

2. 抽象的な名前より、具体的な名前を使います。サーバーのポートで待ち受けを開始できるか調べるなら、ServiceCanStart() より CanListenOnPort() の方が明確です。

3. まず意味が伝わることを優先し、適切なメソッド名なら長さだけを心配する必要はありません。ただし、長すぎる名前は、そのメソッドの責務が多すぎる兆候でもあります。単一責任の原則を意識し、分割できないか検討してください。

   意味が伝わることを前提に、不要な単語を省いたり、理解される省略形を使ったりして簡潔にします。次の例を見てください。

   1. UserDao.findUserById() は UserDao.findById() に短縮できます。DAO インターフェースという文脈から、ユーザーを検索することが既に分かるためです。
   2. この例では、void updateUserForName(String name) を void updateForName(String name) に短縮しています。
   3. toString の形式を参考に、この例では User convertToUserModel(String uid) を ttoUserModel(String ruleStr) に短縮しています。

4. add、insert、append などは近い意味を持ちますが、正確に使い分け、統一してください。例えば文字列の連結には、add ではなく append を使います。

Spring のメソッド名も参考になります。

1. getBean：単純な入口で、doGetBean を呼び出します。

   ```java
   public Object getBean(String name) throws BeansException {
     return this.doGetBean(name, (Class)null, (Object)null, false);
   }
   ```

2. doGetBean：先にキャッシュを確認し、なければ createBean を呼び出して生成します。

   ```java
   String beanName = this.transformedBeanName(name);
   Object sharedInstance = this.getSingleton(beanName);
   this.createBean(beanName, mbd, args);
   ```

3. createBean：bean の妥当性を確認した後、doCreateBean を呼び出して実際に生成します。

4. doCreateBean：bean を実際に生成します。

### ① Service / DAO 層のメソッド命名規約 :id=h-9bd2e757433d

1. 単一のオブジェクトを取得するメソッドは get で始めます。

2. 複数のオブジェクトを取得するメソッドは list で始め、listObjects のように複数形で終わらせます。

3. 件数などを返すメソッドは count で始めます。

4. 追加するメソッドは save / insert で始めます。

5. 削除するメソッドは remove / delete で始めます。

6. 更新するメソッドは update で始めます。

7. データを取り出す：fetch

8. データを探す：find は一致するデータを探しますが、名前だけで検索結果の存在が保証されるわけではありません。

9. データを検索する：search。探しているデータが存在するとは限りません。

10. query は問い合わせの処理を、find は探す意図を強調します。戻り値の型はインターフェースの契約で決まり、どちらもエンティティー、DTO、コレクション、Optional を返せます。名前だけで型が決まるわけではありません。

## 4. 変数の命名規約 :id=h-8abfdc00229a

### **原則 1：名詞、名詞の組み合わせ、形容詞を使う** :id=h-12be50882dfb

変数は通常、何かのものやその属性を表すため、名詞、名詞の組み合わせ、形容詞を使うと意味を理解しやすくなります。

### **原則 2：用語を統一する** :id=h-254143616ad6

同じプロジェクトや場面では、変数名の用語を統一します。例えば total と sum はどちらも合計を表せますが、同じ意味を表す箇所では、どちらかに統一してください。

1. 定数や変数では、種類を表す名詞を末尾に置くと、名前を識別しやすくなります。

> この規約での正例：startTime / workQueue / nameList / TERMINATED_THREAD_COUNT
> この規約での反例：startedAt / QueueOfWork / listName / COUNT_TERMINATED_THREAD

メソッド内の戻り値に result を使うと、処理の流れが分かりやすくなります。例：userListResult。

2. 【この規約では必須】POJO の Boolean 型フィールドには is 接頭辞を付けないでください。一部のフレームワークでは名前の解釈が食い違い、シリアライズ時にエラーになる場合があります。

   > **説明：** ここで参照する MySQL 規約のテーブル作成規則 1 では、真偽を表す列名に is_xxx を使います。そのため、<resultMap> で is_xxx から xxx への対応を設定します。
   >
   > **反例：** 基本型 boolean のフィールドを isDeleted とし、メソッドも isDeleted() とすると、フレームワークがメソッドから導くプロパティー名は deleted になります。意図したフィールド名と一致せず、プロパティーを取得できなくなり、例外につながります。
3. 定数名はすべて大文字にし、単語をアンダースコアで区切ります。長くなっても、意味を省略せず明確に表してください。
4. コレクション名は型名または複数形の s で終わらせる

Java には List、Map、Set などのコレクションがあります。コレクション変数の名前は、一般に次の 2 通りで付けられます。

- 複数形の s で終わらせる

```java
 List<Student> students = new ArrayList<>();
```

- コレクションの型を接尾辞にする

```java
 List<Student> studentList = new ArrayList<>();
```

どちらの方法も使えるため、状況に合わせて選びます。1 つ目は簡潔で、2 つ目は同じローカルスコープに関連する複数のコレクション型がある場合、区別しやすくなります。例を示します。

```java
List<Student> studentList = new ArrayList<>();
Map<Long, Student> studentMap = Maps.newHashMap();
for (Student stu : studentList) {
  studentMap.put(stu.getId(), stu);
}
```

選び方の目安：

- ローカルスコープに 1 種類のコレクションしかなければ、複数形を勧めます。
- 関連する複数のコレクション型があるなら、型名を末尾に付ける方法を勧めます。
