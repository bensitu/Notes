# GitHub Actionsによる継続的インテグレーション :id=h-19d6ae561d89

学習目標：変更ごとにローカルと同じ検証を自動実行し、失敗したらマージやリリースを止めます。先にGitと各プロジェクトのテストコマンドを習得してください。

**適用範囲：**&#x47;itHub Actionsのホスト型Linux runnerです。テンプレートの第三者Actionは完全なコミットSHAで固定し、実行環境はJava 25、Node 24、Python 3.15、uvのバージョンを固定します。

## CI、継続的デリバリー、自動デプロイ :id=h-b5910bd7b0f6

CIは変更を頻繁に統合して自動検証することです。継続的デリバリーはソフトウェアをリリース可能な状態に保ち、自動デプロイは条件を満たした後に成果物を対象環境へ配置します。3つの概念は関連しますが、同じスイッチではありません。

ワークフローはイベントをきっかけにjobを実行し、jobはrunner上で複数のstepを実行します。異なるjobのファイルシステムは既定で共有されないため、成果物のアップロードとダウンロードを明示します。

<a id="section-2"></a>

## そのまま導入できる完全なテンプレート :id=h-d5636eb30d7e

完全なファイルは[learning-examples.yml](examples/taskboard/ci/learning-examples.yml)を参照してください。自分のリポジトリのルートに.github/workflowsを作成し、ファイルをコピーします。パスはリポジトリにexamples/taskboardがあることを前提にしています。

```powershell
New-Item -ItemType Directory -Force .github/workflows
Copy-Item examples/taskboard/ci/learning-examples.yml .github/workflows/learning-examples.yml
```

同名のワークフローがある場合は、直接上書きせず先に内容を比較してください。examples内のテンプレートは自動実行されません。標準のワークフローディレクトリにコピーしてコミットすると、push、pull_request、手動イベントで実行されます。

<a id="section-3"></a>

## テンプレートの実行内容 :id=h-2728fca57ce1

| job      | 主な検証                        | 成果物              |
| -------- | --------------------------- | ---------------- |
| java     | mvn verify                  | テスト済みのJAR        |
| frontend | npm ci、テスト、型チェック、ビルド        | dist             |
| python   | ロックに従うインストール、Ruff、pytest    | テスト結果            |
| browser  | 実際のバックエンドを起動してPlaywrightを実行 | 実際のログインとタスク操作の結果 |

重複作業を減らすため、browser jobは起動用のJARをテストを省略してビルドします。独立したjava jobは完全なテストを実行する必要があります。リリースの条件はbrowserだけでなく、必須のすべてのjobの成功に依存させます。

<a id="section-4"></a>

## ロックファイル、キャッシュ、成果物 :id=h-eba7fa3323f4

npm ciはロックファイルを確認し、uv sync --lockedは依存関係の宣言とロックが不一致なら失敗します。CIで依存関係を自動更新し、「たまたまインストールできた」ことを再現可能なビルドとして扱わないでください。

キャッシュはダウンロードの高速化に、成果物は今回のビルド結果の受け渡しに使用します。キャッシュは無効化や置換があり得るため、唯一のリリース元にしてはいけません。成果物には元のコミット、ビルド番号、チェックサム、保持期間を記録します。

テンプレートはJARとdistをアップロードし、7日間保持します。正式なリリースにはイメージのビルド、スキャン、リポジトリの権限、環境の保護も必要です。テンプレートは本番サーバーが設定済みであるとはしていません。

<a id="section-5"></a>

## 権限と信頼できない入力 :id=h-c936a92cc788

既定ではcontents:readだけを付与します。イメージ公開やデプロイ時は、該当jobだけに必要な権限を追加します。信頼するクラウドはOIDCで短期認証情報を発行できますが、許可するリポジトリ、ブランチ、環境の制限は必要です。

外部のPRのコードを、本番の秘密情報を持つ環境で実行しないでください。PRのタイトルやブランチ名などの信頼できない値を、シェルスクリプトに直接埋め込んではいけません。必要な場合は引数や環境変数で渡し、正しく引用します。

ActionのSHA固定は永久に更新しないという意味ではありません。配布元、保守状況、変更内容を確認してから固定値を更新します。

## 検証と障害箇所の特定 :id=h-6fde756191b8

同じコマンドをローカルで実行できることを確認してから、ワークフローをコミットします。GitHub Actionsで失敗したjob、step、最初のエラーを確認し、必要なレポートをダウンロードします。

| 現象                  | 確認事項                              |
| ------------------- | --------------------------------- |
| ローカルでは成功するがCIでは失敗する | 実行環境のバージョン、大文字と小文字、パス、タイムゾーン、環境変数 |
| CIが起動しない            | ファイル配置、イベント、ブランチフィルター、YAML        |
| ビルドは成功するが成果物がない     | アップロードパスとif-no-files-foundの設定     |
| テスト失敗でもリリースされる      | リリースjobのneeds、条件、終了コード            |
| forkのPRにsecretsがない  | 通常の権限境界であり、権限を広げて回避しない            |

失敗が実際にマージを阻止するよう、必須チェックをブランチ保護やリポジトリ規則に設定します。リモートのワークフローの成功は実際のリポジトリで実行して確認する必要があり、ローカルのYAML解析では代用できません。
