## 1. SSM の連携 :id=h-a9c992ac6492

これまで `Mybatis`、`Spring`、`SpringMVC` の3つのフレームワークを学びました。今回はこれらを連携し、業務機能を開発することが中心です。手順に沿って学んでいきます。

### 1.1 手順の整理 :id=h-fff9713e4894

(1) プロジェクトの作成

- Maven の Web プロジェクトを作成する
- pom.xml に SSM が必要とする依存 jar を追加する
- Web プロジェクトの入口となる設定クラスを作成し、`AbstractAnnotationConfigDispatcherServletInitializer` を実装して次のメソッドをオーバーライドします。
  - getRootConfigClasses()：Spring の設定クラスを返す → ==SpringConfig== 設定クラスが必要
  - getServletConfigClasses()：SpringMVC の設定クラスを返す → ==SpringMvcConfig== 設定クラスが必要
  - getServletMappings()：SpringMVC が処理するリクエストパスの規則を設定する
  - getServletFilters()：フィルターを設定し、POST リクエストの中国語の文字化けを解消する

(2) SSM の連携［==各設定の記述が重点==］

- SpringConfig
  - @Configuration で設定クラスであることを示す
  - @ComponentScan で Service のパッケージをスキャンする
  - Service 層で トランザクション を管理する：@EnableTransactionManagement
  - 外部の properties 設定ファイルを読み込む：@PropertySource
  - Mybatis の連携に必要な設定クラスを導入する：@Import
    - 外部データソースの設定クラス：JdbcConfig
      - DataSource データソース DruidDataSouroce を構築し、データベース接続の4項目を注入する：@Bean @Value
      - プラットフォームの トランザクション マネージャー DataSourceTransactionManager を構築する：@Bean
    - Mybatis の設定クラス：MybatisConfig
      - SqlSessionFactoryBean を構築し、別名のスキャンとデータソースを設定する：@Bean
      - MapperScannerConfigurer を構築し、DAO 層のパッケージスキャンを設定する
- SpringMvcConfig
  - @Configuration で設定クラスであることを示す
  - Controller のパッケージをスキャンする：@ComponentScan
  - SpringMVC のアノテーションサポートを有効にする：@EnableWebMvc

(3) 機能モジュール［具体的な業務モジュールによって異なる］

- データベースのテーブルを作成する
- データベースのテーブルに対応するモデルクラスを作成する
- Dao 層でテーブルの CRUD を実装する（インターフェースと自動プロキシ）
- Service 層を作成する［Service インターフェースと実装クラス］
  - @Service
  - @Transactional
  - Junit と連携して業務層を単体テストする
    - @RunWith
    - @ContextConfiguration
    - @Test
- Controller 層を作成する
  - リクエストを受け付ける：@RequestMapping @GetMapping @PostMapping @PutMapping @DeleteMapping
  - データを受け取る：単純型、POJO、入れ子の POJO、コレクション、配列、JSON 型
    - @RequestParam
    - @PathVariable
    - @RequestBody
  - 業務層に処理を渡す
    - @Autowired
  - 結果を返す
    - @ResponseBody

```java
public class JdbcConfig {
    @Value("${jdbc.driver}")
    private String driver;
    @Value("${jdbc.url}")
    private String url;
    @Value("${jdbc.username}")
    private String username;
    @Value("${jdbc.password}")
    private String password;

    @Bean
    public DataSource dataSource(){
        DruidDataSource dataSource = new DruidDataSource();
        dataSource.setDriverClassName(driver);
        dataSource.setUrl(url);
        dataSource.setUsername(username);
        dataSource.setPassword(password);
        return dataSource;
    }

    @Bean
    public PlatformTransactionManager transactionManager(DataSource dataSource){
        DataSourceTransactionManager ds = new DataSourceTransactionManager();
        ds.setDataSource(dataSource);
        return ds;
    }
}
```

```java
        return true;
    }

    public boolean update(Book book) {
        bookDao.update(book);
        return true;
    }

    public boolean delete(Integer id) {
        bookDao.delete(id);
        return true;
    }

    public Book getById(Integer id) {
        return bookDao.getById(id);
    }

    public List<Book> getAll() {
        return bookDao.getAll();
    }
}
```

**説明：**

- Service に bookDao を注入すると赤い下線が表示されます。なぜでしょうか。

  - BookDao は実装クラスのないインターフェースです。インターフェースはインスタンス化できないため、最終的に注入するのはプロキシオブジェクトです。
  - プロキシオブジェクトは Spring の IOC コンテナーが作成して管理します。
  - IOC コンテナーは Web サーバーの起動時に作成されます。
  - IDEA が依存関係を検査するときは、注入できる適切なクラスが見つからず、エラーを表示します。
  - ただし、実行時にはプロキシオブジェクトが生成され、フレームワークが DI で注入するため、動作には影響しません。

- この問題にはどう対処すればよいでしょうか。

  - 正常に実行できるため、そのままにする

  - エラー表示の重要度を変更する

- フレームワーク内部の例外：不適切な使用が原因
- データ層の例外：外部サーバーの障害が原因（例：サーバーへのアクセスのタイムアウト）

### 3.3 プロジェクトの例外処理方針 :id=h-df13c927174f

#### 3.3.1 例外の分類 :id=h-4ba1e28045a9

例外ハンドラーを使用できるようになりました。実際のプロジェクトでは、どのように例外を処理すればよいでしょうか。

例外には多くの種類があります。それぞれに @ExceptionHandler のメソッドを作ると数が多くなるため、処理する前に分類します。

- 業務例外（BusinessException）

  - 通常の業務フローで操作を完了できない場合

    - 年齢欄に文字列を入れるなど、ユーザーが指定の形式に従わず入力した場合

      ![1630659599983](Resources/1630659599983.png)

  - 不適切なユーザー操作によって発生する例外

    - 例：ユーザーが意図的に誤ったデータを送信する

      ![1630659622958](Resources/1630659622958.png)

- システム例外（SystemException）

  - 実行中に予測できても避けられない例外
    - 例：データベースやサーバーの停止

- その他の例外（Exception）

  - 使用するファイルが存在しないなど、開発者が想定していなかった例外

    ![1630659690341](Resources/1630659690341.png)

例外を分類したら、種類ごとに具体的な対処方法を用意します。

#### 3.3.2 例外への対処方法 :id=h-60e7de99dcb1

- 業務例外（BusinessException）
  - 適切なメッセージをユーザーに返し、正しい操作を促す
    - よくある例は「ユーザー名はすでに存在します」「パスワードの形式が正しくありません」などです。
- システム例外（SystemException）
  - 定型のメッセージをユーザーに返し、状況を案内する
    - システムが混み合っています。しばらくしてから再度お試しください。
    - システムは保守・更新中です。しばらくしてから再度お試しください。
    - システムに問題が発生しました。システム管理者にお問い合わせください。
  - 運用担当者に具体的な通知を送り、対応を依頼する
    - SMS、メール、社内の通信ツールなどで通知できます
  - ログを記録する
    - 通知とログ記録はバックエンド側の処理であり、ユーザーには見えません。
- その他の例外（Exception）
  - 定型のメッセージをユーザーに返し、状況を案内する
  - 開発者に具体的な通知を送り、修正と想定範囲への追加を依頼する
    - 通常は null チェックの漏れなど、考慮不足が原因です
  - ログを記録する

### 5.1 インターセプターの概念 :id=h-89d1bf1dee84

インターセプターの概念を説明する前に、次の図を見てみましょう。

![1630676280170](Resources/1630676280170.png)

(1) ブラウザーからのリクエストは、まず Tomcat Web サーバーに到達します。

(2) Tomcat は、リクエストの対象が静的リソースか動的リソースかを判定します。

(3) 静的リソースなら、Tomcat のプロジェクト配備ディレクトリから直接アクセスします。

(4) 動的リソースなら、プロジェクトのバックエンドコードに処理を渡します。

(5) 具体的なメソッドに到達する前に、設定したフィルターを順番に実行します。複数のフィルターを設定できます。

(6) その後、中央ディスパッチャー（SpringMVC の一部）へ進み、SpringMVC が設定規則に従ってリクエストを捕捉します。

(7) 規則に一致すれば、対応する controller クラスのメソッドを見つけて実行し、結果を返します。

(8) 規則に一致しなければ処理しません。

(9) 各 Controller メソッドの実行前後に処理を追加するには、どうすればよいでしょうか。

これがインターセプターの役割です。

- インターセプター（Interceptor）は、メソッド呼び出しを動的に捕捉する仕組みです。SpringMVC ではコントローラーメソッドの実行を捕捉します。
- 役割：
  - 指定したメソッドの呼び出し前後に、あらかじめ設定したコードを実行する
  - 元のメソッドの実行を止める
  - まとめると、インターセプターは既存の処理を拡張するためのものです。

ここまでを見ると、次のことに気付きます。

- インターセプターとフィルターは、役割や実行順序が似ています。

では、インターセプターとフィルターにはどのような違いがあるのでしょうか。

- 所属が異なります。Filter は Servlet 技術、Interceptor は SpringMVC 技術に属します。
- 対象が異なります。Filter はすべてのアクセスを拡張し、Interceptor は SpringMVC へのアクセスだけを拡張します。

#### 5.3.1 前処理メソッド :id=h-93bca170325b

元のメソッドの前に実行される：preHandle

```java
public boolean preHandle(HttpServletRequest request,
                         HttpServletResponse response,
                         Object handler) throws Exception {
    System.out.println("preHandle");
    return true;
}
```

- request：リクエストオブジェクト
- response：レスポンスオブジェクト
- handler：現在のハンドラーオブジェクトです。アノテーション付きのコントローラーでは通常 HandlerMethod ですが、静的リソースなどのハンドラーは別の型の場合があります。キャスト前に型を確認してください。

request オブジェクトで、リクエストヘッダーの `Content-Type` などのリクエストデータを取得できます。

```java
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
    String contentType = request.getHeader("Content-Type");
    System.out.println("preHandle..."+contentType);
    return true;
}
```

handler 引数で、メソッドに関する情報を取得できます。

```java
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
    HandlerMethod hm = (HandlerMethod)handler;
    String methodName = hm.getMethod().getName();// See note 1 below.
    System.out.println("preHandle..."+methodName);
    return true;
}
```

例の説明：

1. メソッド名を取得できる

#### 5.3.2 後処理メソッド :id=h-4ef4f8585e28

元のメソッドの実行後に動作します。元のメソッドが阻止された場合は実行しません。

```java
public void postHandle(HttpServletRequest request,
                       HttpServletResponse response,
                       Object handler,
                       ModelAndView modelAndView) throws Exception {
    System.out.println("postHandle");
}
```

最初の3つの引数は、上と同じです。

modelAndView：ハンドラーの実行後に結果がある場合、対応するデータやページ情報を読み取り、調整できます。

現在は json データを返しているため、この引数を使う機会は多くありません。

#### 5.3.3 完了処理メソッド :id=h-dbf5bd70d8dd

リクエスト完了後に呼び出されますが、preHandle が正常に true を返したインターセプターだけが対象です。現在のインターセプターが false を返すと、その afterCompletion は呼び出されません。それより前に通過を許可したインターセプターには、完了コールバックが行われます。

```java
public void afterCompletion(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler,
                            Exception ex) throws Exception {
    System.out.println("afterCompletion");
}
```

最初の3つの引数は、上と同じです。

ex：ハンドラーの実行中に例外が発生した場合、その例外に応じた個別の処理ができます。

現在はグローバルな例外ハンドラークラスがあるため、この引数も使う機会は多くありません。

この3つの中で最もよく使うのは ==preHandle== です。戻り値で通過を許可するかを決定できます。業務ロジックをここに記述し、条件を満たせば true、満たさなければ false を返して処理を止めます。

手順3：プログラムを実行して順序を確認する

![1630680435269](Resources/1630680435269.png)

実行順序は設定順序に依存します。前に挙げた運用担当者がサーバールームへ入る例と同じく、先に入ったものが後に出ます。

- 複数のインターセプターを設定すると、インターセプターチェーンになります。
- インターセプターチェーンの実行順序は、追加した順序に基づきます。
- 元のハンドラーの実行を止めるインターセプターがあると、それ以降のインターセプターはすべて実行されなくなります。
- インターセプターの処理が中断された場合は、それより前に設定したインターセプターの afterCompletion 処理だけが実行されます。

![1630680579735](Resources/1630680579735.png)

preHandle：設定順に実行します。前の処理が false を返すか例外を送出すると、後続は実行されません。

postHandle：設定と逆の順序で実行し、実行されない場合もあります。

afterCompletion：設定と逆の順序で実行し、実行されない場合もあります。

この順序を覚えにくい場合は、==実際の実行結果を基準にする== という原則を押さえてください。
