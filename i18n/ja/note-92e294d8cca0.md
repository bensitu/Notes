# ログイン認証とアクセス制御 :id=h-e697a94d00dc

学習目標：正当なユーザーが許可されたリソースにアクセスできるようにし、ログイン、セッション、CSRF、権限検証それぞれの役割を理解します。先にHTTPとWebセキュリティのドキュメントを読んでください。

**適用範囲：**&#x5B8C;全なサンプルはSpring Boot 4が管理するSpring Security、サーバー側Session、メモリ内のデモアカウントを使用します。外部公開にはHTTPS、実際のユーザーストレージ、アカウントのライフサイクル管理が必要です。

## まず3つの問いを区別する :id=h-f4f98e79a0f0

| 問い        | 意味            | 例                   |
| --------- | ------------- | ------------------- |
| 認証        | あなたは誰か？       | パスワードでログインしセッションを作成 |
| 認可        | 何ができるか？       | 管理者は削除可能            |
| リソースの所有関係 | どのデータを操作できるか？ | 一般ユーザーは自身のタスクのみ変更可能 |

フロントエンドのボタンを隠しても表示に影響するだけで、APIの直接呼び出しは防げません。ロールの検証だけでオブジェクトの所有関係も自動検証されるわけではありません。

<a id="section-2"></a>

## 実行可能な完全なフロー :id=h-4ba65a202e1e

1. プロジェクトの説明に従ってバックエンドとフロントエンドを起動します。
2. フロントエンドはGET /api/csrfを送信し、Cookieを保存して、リクエストヘッダー名とトークンを取得します。
3. POST /api/loginに、URLでエンコードしたフォームとしてアカウントとパスワードを送り、CSRFヘッダーを付加します。
4. ログイン成功後にCSRFトークンを再取得し、それからタスクを作成または更新します。
5. POST /api/logoutにも同じくトークンを付け、ログアウト後はページの共有状態を空にします。

[完全なセキュリティ設定](examples/taskboard/backend/src/main/java/example/tasks/SecurityConfig.java)と[ブラウザーのリクエスト処理](examples/taskboard/frontend/src/api.ts)を合わせて使用します。ユーザー名はadmin、パスワードはAPP_PASSWORDから読み取ります。ローカルのフォールバック値は練習専用で、外部公開には使用しません。

<a id="section-3"></a>

## CookieとCSRFの詳細 :id=h-a42bd3fccba8

Sessionの識別子はHttpOnly Cookieに保存し、フロントエンドが読み取る必要はありません。fetchは同一オリジンの認証情報設定を使用し、開発ではVite、本番ではNginxのプロキシで同一オリジンを保ちます。

サンプルはSpring Securityの既定のCSRF保護を維持し、「APIがJSONを返す」ことを理由に無効化しません。Cookie認証の書き込み操作にはリクエスト保護が必要です。

ログインやログアウト後にトークンが変わる場合があります。最初のトークンを長期間キャッシュせず、URLやログに記録しないでください。403ではまず認可失敗とトークン不一致を区別します。

<a id="section-4"></a>

## パスワード、ユーザー、本番運用までの不足事項 :id=h-f0ba523b9983

PasswordEncoderはアルゴリズム識別子付きのパスワードハッシュを作成します。ハッシュは復元可能な暗号化ではありません。検証にはmatchesを使用し、自分で再エンコードして文字列比較しないでください。ランダムなソルトにより、同じパスワードでも異なるエンコード結果になります。

この例は起動ごとにメモリ内のアカウントを作成します。実システムではハッシュを保存し、無効化、権限変更、パスワード再設定、ログインのレート制限、必要な監査に対応します。ユーザーのパスワードをタスクのフィールドと一緒に返してはいけません。

ユーザーの所有関係を追加したら、データベース操作はユーザーIDも条件に含める必要があります。構文の例は次のとおりです。

```sql
SELECT id, title FROM task WHERE id = ? AND owner_id = ?;
```

現在のサンプルテーブルにはowner_idがなく、そのまま実行できません。マイグレーションで列を追加し、既存データを補完し、認可を実装して越権アクセスのテストを追加して初めて、複数ユーザーの分離に対応したと言えます。

<a id="section-5"></a>

## OAuth2、OIDC、JWTの位置付け :id=h-ca53ec5d4f13

OAuth2は認可の委任を扱い、OIDCはその上に認証の層を提供し、JWTはトークンの形式です。シングルサインオンが必要なら信頼できるIDプロバイダーと連携し、初心者が完全な認可サーバーを自作することは推奨しません。

ブラウザーで認可コードフローとPKCEを使用しても、リダイレクト先やstateなどの結び付け情報を確認する必要があります。JWTはデコードだけでは検証できず、取り決めに従って署名、発行者、対象者、有効期限、許可するアルゴリズムも検証します。

トークンがJWTだからといって永久に有効と扱わないでください。ログアウト、失効、権限変更、漏えいへの対応が必要です。SessionとTokenはクライアントとデプロイ形態に合わせて選びます。

<a id="section-6"></a>

## 検証と開発の早見表 :id=h-798d43a11818

| テストケース               | 期待する結果           |
| -------------------- | ---------------- |
| 未ログインでタスクを読む         | 401              |
| ログイン済みだが書き込みにCSRFがない | 403              |
| 一般ロールによる削除           | 403              |
| 管理者が有効なトークンで削除       | 204、リソース不存在なら404 |
| ログアウト後に再度読む          | 401              |
| ユーザーAがユーザーBのリソースを操作  | 複数ユーザー対応後は必ず拒否   |

バックエンドのテストは模擬IDで権限規則を確認し、ブラウザーのエンドツーエンドテストは実際のパスワードログイン、Cookie、CSRFの連携を確認します。両者は互いの代わりにはなりません。
