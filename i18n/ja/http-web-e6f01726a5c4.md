## リクエストと応答とは :id=h-707b0705c879

リクエストにはメソッド、対象、ヘッダー、任意の本文が含まれ、応答にはステータスコード、ヘッダー、任意の本文が含まれます。JSONは内容の形式であり、通信プロトコルではなく、認証や暗号化を自動的に提供しません。

| メソッド   | このプロジェクトの用途  | 繰り返しリクエストする際の注意                      |
| ------ | ------------ | ------------------------------------ |
| GET    | タスクの読み取り     | 業務状態を変更すべきではない                       |
| POST   | タスク作成またはログイン | ネットワークのタイムアウト後に再送すると重複作成の可能性がある      |
| PUT    | タスクの新しい内容を送信 | 例ではバージョン条件があり、古いバージョンの再送は409になる場合がある |
| DELETE | 指定タスクの削除     | 連続した削除で応答ステータスは異なっても、削除後の対象状態は同じ     |

冪等性は複数回実行した際の想定効果を表し、毎回完全に同じ応答を要求しません。支払いや注文などのPOSTで再試行を許可する場合は、アプリ独自の冪等性キーとデータベース制約が必要です。

## 最小限の練習：実際の応答を観察する :id=h-a665f96b1dd4

まずサンプルプロジェクトのバックエンドを起動します。

```powershell
curl.exe -i http://127.0.0.1:8080/actuator/health
curl.exe -i http://127.0.0.1:8080/api/tasks
curl.exe -i http://127.0.0.1:8080/api/csrf
```

200、401、CSRF JSONをそれぞれ観察します。CSRFの応答でセッションも作成される場合があり、コマンドラインではCookieを保存してログインを続ける必要があります。ブラウザーのフロントエンドにはこの処理がまとめられています。

| ステータス           | 一般的な意味                                                |
| --------------- | ----------------------------------------------------- |
| 200 / 201 / 204 | 読み取りまたは変更成功 / 作成済み / 成功、応答本文なし                        |
| 400 / 422       | 入力がAPIの取り決めに不適合。このプロジェクトのJavaは400、Pythonの既定の検証は422を使用 |
| 401 / 403       | 未認証 / 権限またはリクエスト保護の検証に失敗                              |
| 404 / 409       | リソース不存在 / 現在のリソース状態との競合                               |
| 500 / 502 / 504 | アプリ内部エラー / プロキシの上流異常 / 上流待機のタイムアウト                    |

## Cookie、Session、Token :id=h-709e78586962

Cookieはドメイン、パス、有効期限などの規則に従ってブラウザーが付加するデータです。Sessionはサーバーがセッション状態を保持する方式で、通常はCookieでセッション識別子を渡します。JWTはトークンの形式であり、OAuth2と同義ではなく、ログアウト、漏えい、権限変更への対応を省略できるわけでもありません。

HttpOnlyはスクリプトによるCookieの読み取りを制限し、Secureは安全な接続での送信を要求し、SameSiteは一部のクロスサイト送信を制御します。それぞれ役割があり、権限検証やすべてのCSRF対策の代わりにはなりません。

## 混同しやすい4つの問題 :id=h-d4fdc3511d04

| 問題          | 例                                   | 対策                                            |
| ----------- | ----------------------------------- | --------------------------------------------- |
| XSS         | ユーザー入力をHTMLやスクリプトとして実行する            | 原則テキストとして出力し、リッチテキストを制限し、必要なら信頼できるサニタイズツールを使用 |
| CSRF        | ブラウザーがログインCookieを付けてユーザーの意図しない操作を行う | CSRFトークン、適切なCookie設定、送信元の検証                   |
| SQLインジェクション | 入力をSQLの構造へ組み込む                      | パラメーターのバインド。動的テーブル名とソート項目にはプログラムの許可リスト        |
| 権限を超えるアクセス  | URLのタスクIDを変更して他人のタスクを読む             | サーバーで現在のユーザーとタスクの所有関係を確認                      |

CORSはクロスオリジンの読み取りに対するブラウザーの制御です。CORSを許可してもユーザーはログインせず、業務権限も得られません。ブラウザー以外のクライアントには同じ読み取り制限は適用されません。

## キャッシュ、HTTPS、境界 :id=h-5d9a8c914b9d

内容のハッシュ付き静的リソースは長期キャッシュに適し、HTMLのエントリーポイントは再検証できるようにします。個人データとトークンを共有キャッシュに入れてはいけません。ETagとIf-None-Matchは条件付きリクエストに使用でき、304は業務の失敗ではありません。

HTTPSは通信を保護しますが、接続先のドメインと証明書の有効性も確認します。本番接続の修正のために証明書検証を無効にしないでください。プロキシは既知のプロキシからの転送ヘッダーだけを信頼します。

このプロジェクトはViteまたはNginxで/apiをバックエンドへ転送し、ブラウザーが同一オリジンのアドレスを使用します。開発用プロキシは自動的に本番プロキシになりません。

<a id="section-6"></a>

## 検証と開発の早見表 :id=h-0d003d14ab05

ブラウザーのNetworkパネルでURL、メソッド、ステータス、Content-Type、Cookie、リクエスト本文を記録します。403では権限不足とCSRF不足を先に区別し、401ではまずセッションの期限切れを確認します。

パスワード、Cookie全体、Authorization、CSRFトークンをログに記録しないでください。作成、削除、権限変更のテストは成功だけでなく拒否される経路も検証します。
