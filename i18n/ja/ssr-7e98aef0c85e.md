## 実際のデプロイ形態を先に確認する :id=h-934408950cc3

| ビルド形態               | デプロイ対象                | 前提にしてはいけないこと                          |
| ------------------- | --------------------- | ------------------------------------- |
| React / Vue CSR     | 静的ファイルと独立したAPI        | 開発用プロキシもデプロイされていること                   |
| Next Node SSR       | Nextのサーバー実行環境とビルドファイル | 任意のディレクトリを静的サイトとして配信すればサーバー機能も維持されること |
| Nuxt Node SSR       | .output/serverと関連する出力 | publicをコピーするだけでAPIと動的ページが利用できること      |
| 静的エクスポート / プリレンダリング | 生成された静的コンテンツ          | リクエスト時のすべてのサーバー機能を引き続き使用できること         |

エッジ環境、サーバーレスプラットフォーム、通常のNodeでは、API、ファイルシステム、ライフサイクルが異なります。サンプルはNode 24を使用します。別のプラットフォームにデプロイする前に対応範囲を確認してください。

<a id="section-2"></a>

## 本番環境の最小限の検証 :id=h-c043f426620f

[実行手順](examples/ssr/README.md)に従ってNextとNuxtをビルドし、テストを実行します。開発サーバーの結果を本番の動作の代わりにしないでください。

生のHTML、Cache-Control、応答ステータス、クライアントログを確認します。その後、実際のリバースプロキシを通して再検証し、圧縮、ストリーミング、タイムアウト、リクエスト本文の制限、リソースパスを確認します。

このリポジトリのtaskboard Nginxサービスが転送するのはJava APIであり、新たに追加したNext / Nuxtのポートは自動的にプロキシされません。デプロイ先に合わせて上流とドメインを個別に設定する必要があります。

## キャッシュの前にデータの所有者を確定する :id=h-7ebe3a6a532e

| 内容                             | 基本的な考え方                                |
| ------------------------------ | -------------------------------------- |
| 内容のハッシュを持つ静的リソース               | 長期間キャッシュできる                            |
| 公開記事                           | 有効期限と無効化規則を明確にすれば共有できる                 |
| 識別情報、権限、個人データを含むHTML / payload | まず共有キャッシュを避け、必要に応じて明確な識別情報の境界に基づいて設計する |
| ログイン、ログアウト、Cookieの設定           | 通常の公開ページとしてキャッシュしない                    |
| エラー応答                          | 恒久的な不存在と一時的な障害を区別し、エラーを長期間キャッシュしない     |

キャッシュキーはURLだけでなく、言語、テナント、ユーザー、その他の入力にも依存する場合があります。ブラウザーのキャッシュを無効にするだけでは、サーバーやCDNのキャッシュは自動的に消えません。

Cache-Controlはすべての内部キャッシュを統一的に制御するスイッチではありません。フレームワークのデータキャッシュ、ページキャッシュ、クライアントのナビゲーションキャッシュ、プロキシ、CDNを個別に確認し、更新時は対応する層を無効化します。

## リクエストの状態とBFFの境界 :id=h-30824d8b7e88

Nodeプロセスは複数のユーザーを同時に処理する場合があります。現在のユーザー、Cookie、CSRF、テナントのオブジェクトをモジュールのグローバル変数に保存しないでください。公開の読み取り専用定数は共有できますが、リクエストに関連する可変データは分離します。

サーバーのfetchはブラウザーのfetchと本質的に同じではありません。現在のリクエストの識別情報を信頼する上流へ転送する際は、宛先と許可するヘッダーを制限し、ユーザー指定のURLにCookieやAuthorizationを無条件で転送しないでください。

サーバーが上流のSet-Cookieを取得しても、ブラウザーが受け取ったとは限りません。BFFの設計では、文字列をコピーするだけでなく、Cookieのドメイン、パス、Secure、SameSite、複数値の応答ヘッダーを正しく処理する必要があります。

<a id="section-5"></a>

## データ出力、エラー、ストリーミング応答 :id=h-3800bc8c8b94

クライアントには画面に必要なデータだけを渡します。非公開の環境変数はpublic接頭辞を付けなくても、propsやAPIの応答に書き込むと漏えいする可能性があります。

通常のテンプレートはテキストをエスケープしますが、JSONを手動でscriptに組み込んだり、HTMLを連結したり、危険なHTMLインターフェースを使ったりすると追加のリスクが生じます。フレームワークのシリアライズ機構を使用し、出力を許可するフィールドも確認します。

エラー応答にスタックトレース、SQL、秘密情報を表示しないでください。ストリーミング開始後はHTTPステータスが送信済みの場合があります。ステータスとレンダリング失敗の両方を監視し、最終ページの文言だけで成功と判断しないでください。

<a id="section-6"></a>

## 確認事項と機能の限界 :id=h-72d94a4e7b91

- 独立した2つのセッションで、互いの非公開コンテンツが見えないこと。
- HTML、RSC / Nuxtのpayload、API、ログに不要な秘密情報がないこと。
- 未ログイン、権限不足、リソース不存在、上流障害時の動作が明確であること。
- クライアント切断、タイムアウト、サーバー終了時に対応するリソースを解放できること。
- リリース記録にコード、設定、フレームワークのバージョン、キャッシュ無効化戦略を一緒に保存すること。
- 静的リソースがページと同じビルドバージョンに由来し、リリース中のリソース欠落を防ぐこと。
- プロキシとCDNの環境は実際に検証し、ローカルのテストで代用しないこと。

サンプルは公開記事だけを扱い、本番用のログインやCDNはありません。ブラウザーセッションの分離テストで証明できるのは、このサンプルのカウンター状態が混ざらないことだけであり、完全な認証システムの安全性を示すことはできません。
