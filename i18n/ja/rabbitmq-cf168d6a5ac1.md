# メッセージキューの基礎とRabbitMQの実践 :id=h-07acb114b631

学習目標：非同期の疎結合化、確認応答、再配信、冪等性を理解し、「メッセージ送信」を「業務完了」と扱わないようにします。

**適用範囲：**&#x5B66;習用サーバーはRabbitMQ 4.2です。Pythonのpikaのバージョンはロックファイルを参照してください。サンプルはAMQP 0-9-1、durableなトポロジー、手動確認応答を使用します。先にミドルウェアのコンテナーを起動してください。

## メッセージが通る手順 :id=h-048e030c61d7

プロデューサー → exchangeがrouting keyで振り分け → queueが未処理メッセージを保存 → コンシューマーが業務処理を実行 → コンシューマーが確認応答。

exchangeとqueueは異なります。プロデューサーへの確認はbrokerが送信に対して所定の確認を行ったことだけを示し、コンシューマーの業務完了を証明しません。コンシューマーの確認応答も、プロデューサーが受領通知を受け取った証明にはなりません。

| 仕組み                | 解決する問題                        | 自動的には解決しないこと              |
| ------------------ | ----------------------------- | ------------------------- |
| Publisher confirm  | 送信側がbrokerの確認の有無を知る           | 受信処理が完了したかどうか             |
| mandatory / return | 振り分け不能なメッセージの検出               | 後続処理の失敗                   |
| 手動ack              | 処理後のメッセージの削除                  | コンシューマーのクラッシュのタイミングで生じる重複 |
| デッドレタールーティング       | 拒否された、またはデッドレター条件を満たすメッセージの隔離 | 無限の再試行と手動修復               |
| 冪等性                | 同じイベントが再到着しても効果を重複させない        | すべての外部システムの原子的コミット        |

## 最小限の実行手順 :id=h-e67da6969aa8

まず一貫したサンプルプロジェクトのディレクトリから起動します。

```powershell
docker compose --env-file .env --profile tools up -d rabbit
```

管理画面[http://127.0.0.1:15672](http://127.0.0.1:15672)にログインできるまで待ちます。ユーザー名とパスワードは.envのものを使い、ローカル接続のみに制限された既定のguestアカウントは使用しません。

Pythonプロジェクトへ移動します。

```powershell
Set-Location examples/taskboard/python
uv sync --locked --all-extras
$env:AMQP_URL = 'amqp://notes_user:local_rabbit_change_me@127.0.0.1:5672/%2F'
uv run --locked python -m task_tools.mq_demo publish --event-id demo-001
uv run --locked python -m task_tools.mq_demo consume
```

[完全なコード](examples/taskboard/python/src/task_tools/mq_demo.py)はconsumeごとに1件だけ取得し、キューが空なら正常終了するため、常時動作するバックグラウンドworkerではありません。URLのパスワードに特殊文字がある場合は、正しいパーセントエンコーディングが必要です。

## 確認応答とローカルの業務効果 :id=h-abf7c4753cd0

プロデューサーはconfirmを有効にし、メッセージに永続化フラグを付け、振り分け可能であることを要求します。コンシューマーはまずeventIdと業務効果をローカルのSQLite トランザクションに書き込み、コミット後にのみackします。

同じeventIdが再到着すると、データベースの一意キーが重複挿入を防ぎます。ここで示す「業務効果」はデータベースのレコード1件であり、メールは送信しません。データベースと外部メールサービスを一緒に原子的にコミットできるともしていません。

空の練習用キューで、同じeventIdを使ってpublish / consumeをもう1回行うと、Committed new effect: Falseとなるはずです。キューが空になることだけでなく、handled-events.dbを観察してください。

## デッドレターと失敗処理 :id=h-105cdef1c260

不正なJSON、長すぎるメッセージ、不正なフィールドは拒否され、元のキューへ戻されず、トポロジーに従ってnotes.failedへ送られます。原因を確認して修正し、管理された形で再生します。重複する業務イベントでは元のeventIdを保つことで冪等性の保護を利用できます。

この例は無限ループを防ぐため、SQLiteエラーもデッドレター経路へ送ります。実システムでは一時的な失敗と恒久的な失敗を区別し、上限付きの再試行、遅延、手動復旧手順を設ける必要があります。

デッドレターの転送自体も、キューの種類と可用性の設定に影響されます。「DLXを設定した」ことを、どのような障害でも絶対に失われないという意味で受け取らないでください。

## データベースとメッセージの整合性 :id=h-9d331c0734bf

業務データベースをコミットしてから送信すると、送信前に停止する可能性があります。先に送ってからコミットすると、最終的にロールバックされた業務を通知する可能性があります。一般的には、業務データとoutboxレコードを一緒にコミットし、発行処理が送信と確認を行います。

コンシューマーがコミット後、ack前に停止するとメッセージが再配信されるため、冪等性は通常必要な設計要件です。「普通は1回しか送らない」ことを、重複しない証拠にしてはいけません。

長時間動作するworkerには、接続復旧、適切なprefetch、正常な停止、監視も必要です。複数のコンシューマーでは完了順序が投入順序と一致するとは限りません。順序が必要な業務にはグループ分けと直列実行の制約を明確にします。

## 検証と開発の早見表 :id=h-d3342c037370

| 現象                    | 確認事項                                        |
| --------------------- | ------------------------------------------- |
| confirmは成功するが処理されない   | ルーティング、キューのバインド、コンシューマーの状態、ログ               |
| メッセージが繰り返し現れる         | 失敗時のrequeueとackの忘れを確認                       |
| 同じ通知で効果が2回発生する        | eventIdが安定しているか、効果と重複排除が同じトランザクションか確認       |
| キューのパラメーター競合          | 既存のキューが異なるパラメーターで作られていないか確認し、業務キューを勝手に削除しない |
| 再起動後もレコードはあるが重複排除されない | SQLiteのファイルパス変更や永続ストレージの消失を確認               |

結果不明の操作を再試行する前に状態を照会します。再試行ごとに新しいeventIdを生成すると、一意キーで同じ業務イベントを識別できなくなります。
