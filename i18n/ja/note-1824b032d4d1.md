# バックエンドの自動テスト：動作と失敗経路の検証 :id=h-75905a7a5a16

学習目標：単体、結合、エンドツーエンドの各テストが守るものを理解し、コミット前に意味のある検証を行います。

**適用範囲：**&#x4E00;貫したJavaプロジェクトでは、Spring Boot 4のBOMが管理するJUnit Jupiter、MockMvc、Spring Security Testを使用します。org.junit.jupiter APIを引き続き使用し、古いJUnit 4の注釈とは混用しません。

## テストの層 :id=h-e705fe7ea735

| 層            | 検証するもの                        | 主なコスト                |
| ------------ | ----------------------------- | -------------------- |
| 単体テスト        | 1つの業務規則の入出力                   | 非常に小さい。通常は依存先を分離する   |
| Webテスト       | ルーティング、バインド、検証、ステータス、セキュリティ規則 | Webのテスト環境が必要         |
| データベースの結合テスト | SQL、マッピング、トランザクション、制約         | データベースが必要            |
| エンドツーエンドテスト  | 実際のログインからページ操作までの全経路          | 比較的遅く、調査がコンポーネントをまたぐ |

アサーションは業務上の結果を表すべきです。メソッドの呼び出しや「例外が出なかった」だけの確認では、通常、重要な動作を守るには不十分です。

<a id="section-2"></a>

## 最小限の実行手順 :id=h-f93d522c75e4

```powershell
Set-Location examples/taskboard/backend
mvn -B -ntp verify
```

完全なテストは[TaskApiTest.java](examples/taskboard/backend/src/test/java/example/tasks/TaskApiTest.java)、レポートはtarget/surefire-reportsを参照してください。失敗時は最初のアサーションと根本原因を確認し、最後のMavenエラー行だけで推測しないでください。

<a id="section-3"></a>

## この例が実際に検証する内容 :id=h-ff913d3d8512

- 匿名でのタスク読み取りは401を返します。
- 認証済みでもCSRFがない書き込みは403を返します。
- 空白のタイトルは400を返します。
- タスク作成は201とLocationを返します。
- 同じ古いバージョンの書き込みを繰り返すと409を返します。
- 一般ロールは削除できず、管理者は削除できます。
- 削除後の読み取りは404を返します。

模擬IDを使ってもセキュリティシステム全体を模擬するわけではなく、フィルターは引き続き処理に参加します。パスワードログイン、Cookie、トークン更新は別途ブラウザーテストで検証します。

## トランザクションとテストデータ :id=h-22c399716ab6

テストクラスは@Transactionalを使い、同じスレッドのMockMvcリクエストによるDB変更をテスト後にロールバックします。実際のポートへリクエストするとサーバーは別スレッドで処理するため、テストスレッドのトランザクションがサーバーの処理を自動でロールバックするわけではありません。

各テストは自身のデータを作成し、実行順序、固定の自動採番キー、前のテストの残骸に依存しません。時刻、乱数、外部APIは入力を制御できるようにして、失敗を繰り返し再現できるようにします。

欠落、重複、長さの境界、権限拒否、リソース不存在、競合更新はそれぞれケースを設計します。すべてを巨大な1つのテストに詰め込んで、失敗箇所を分かりにくくしないでください。

<a id="section-5"></a>

## 実データベースとTestcontainers :id=h-3eb360170f30

既定のテストは高速なH2を使用しますが、MySQLの方言、ロック範囲、MongoDB / Redis / RabbitMQの動作は検証しません。

Dockerをインストールすると、Testcontainersで独立した実データベースをテスト用に作成できます。拡張にはBoot 4と互換性のある依存関係を選び、JDBC URLを変えるだけでなく、接続のライフサイクル、マイグレーション、データ削除を明確にします。

このリポジトリにはDocker Composeを使うMySQLの実行手順もあります。最小限の検証は、実サービスの起動、マイグレーションの適用、同じ読み書きと競合ケースの実行、独立した2接続でのロック待機テストです。

## よくあるエラーと開発の早見表 :id=h-be365f4e9286

| 誤り                          | 結果                             | 改善                  |
| --------------------------- | ------------------------------ | ------------------- |
| 古いJUnit 4の注釈とJupiterエンジンを併用 | テストが実行されない、またはライフサイクルが機能しない可能性 | インポートとエンジンを統一       |
| 外部サービスが失敗するとすべてのアサーションを省略   | CIが成功表示でも検証していない               | 明確に失敗させるか結合テストを別に分類 |
| 複数のテストで固定レコードを共有            | 順序変更で失敗                        | 各テストが独自のデータを持つ      |
| HTTP 200だけを確認               | 誤った内容や状態を見逃す可能性                | 意味、応答、データの結果を合わせて確認 |
| 実装の細部をテストへコピー               | リファクタリングで無意味な失敗が大量に発生          | 観察可能な動作を確認          |

CIではテスト失敗が後続リリースを阻止するようにします。終了コードの無視や既定のテスト省略で成功表示を得てはいけません。
