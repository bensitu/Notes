# MVC と Java Web アプリの階層構造 :id=h-7ba3ec40b317

MVC、3 層アーキテクチャー、よく使うデータオブジェクトを区別し、開発時の責務と依存の方向を決めます。

**前提知識とバージョン：** Java のクラス、インターフェース、基本的な HTTP の知識が必要です。設計上の責務を説明するもので、すべてのプロジェクトに同じディレクトリやクラス名を要求するものではありません。

**画面例について：** 画像には元の学習環境での操作を残しています。古い画面の書き方と本文が異なる場合は、修正後の本文と、選んだバージョンの公式ドキュメントを優先してください。

**サンプルの使い方：** 全ファイルと実行手順を明示したプロジェクトを除き、各コードブロックは節ごとの独立した断片です。省略部分や仮の名前を補ってください。誤りと示した行は問題の説明用です。同じ節の代替実装を混ぜないでください。

## MVC の 3 つの責務 :id=h-549c1e38412c

MVC は Model（モデル）、View（ビュー）、Controller（コントローラー）の略です。

| 構成要素       | 責務                             | よくある例                          |
| ---------- | ------------------------------ | ------------------------------ |
| Model      | 業務データと業務処理の機能を表す               | ユーザーオブジェクト、注文サービス              |
| View       | データを表示し、操作画面を提供する              | HTML、Thymeleaf テンプレート、Vue のページ |
| Controller | リクエストを受け、業務処理を呼び出し、レスポンスを組み立てる | Spring MVC のコントローラー            |

**Mapper は MVC の M ではなく、Controller も View ではありません。** MVC は責務の分け方であり、固定された 3 つの Java パッケージではありません。

## MVC と 3 層アーキテクチャー :id=h-9fc33017ea40

Java の Web バックエンドでは、表示、業務処理、データアクセスの層に分けることがよくあります。MVC はビュー、コントローラー、モデルの連携を表すもので、この 3 層と単純に 1 対 1 で対応するわけではありません。

```text
Browser -> Controller -> Service -> DAO / Mapper -> Database
Browser <- Controller <- Service <- DAO / Mapper <- Database
```

- Controller：パス、パラメーター、リクエスト本文を受け取り、入力を検証し、Service を呼び出してページやデータを返します。
- Service：業務ルールを実装し、トランザクションをまとめます。例えば注文処理は、在庫と注文の両方に関係します。
- DAO / Mapper：ユーザー検索や在庫更新など、データベースへのアクセスを担当します。

依存は通常、上位から下位へ向かいます。Controller は Service に、Service は DAO に依存します。下位の層から上位の層を呼び出さないようにします。上位層はインターフェースに依存し、注入によって実装を受け取れます。

## よく使うオブジェクト名 :id=h-9b32368c66eb

| 名前               | 意味                                    | 使い方                                                 |
| ---------------- | ------------------------------------- | --------------------------------------------------- |
| POJO             | Plain Old Java Object：通常の Java オブジェクト | 特定のフレームワークを必要とせず、getter/setter も必須ではない。永続化用途も排除しない  |
| Entity / PO / DO | 永続化するデータを表すオブジェクト                     | テーブルの列に対応することが多いが、どのシステムでも 1 クラス 1 テーブルが必須というわけではない |
| DTO              | Data Transfer Object：データ転送オブジェクト      | インターフェースや層の間でデータを渡し、呼び出し元に必要なフィールドだけを持つ             |
| VO               | View Object：表示用のオブジェクト                | ページや API レスポンスに必要なフィールドをまとめる                        |
| DAO              | Data Access Object：データアクセスオブジェクト      | データベースへアクセスするメソッドをまとめる                              |
| Domain           | ドメインモデル                               | 業務の概念や規則を表し、複数のテーブルを結合した大きなオブジェクトというだけのものではない       |

これらの名前の使い方はチームによって異なります。まず用途を決め、その後で命名を統一してください。例えばデータベースのユーザーレコードにはパスワードのハッシュがあっても、ユーザー一覧には番号とニックネームしか必要ありません。UserView を返せば、機密フィールドをフロントエンドへ公開せずに済みます。

## 各層の間でデータを渡す :id=h-6a2bc214a250

```text
JSON request -> CreateUserRequest -> Service -> UserEntity -> Database
JSON response <- UserView <- Service <- UserEntity <- Database
```

単純な検索なら DTO を直接返せます。複雑な業務処理ではドメインオブジェクトを導入できます。VO、DTO、DO を増やすかは責務によって決め、すべてのリクエストで 6 種類のオブジェクトや 4 回の変換を用意する必要はありません。

## ディレクトリ構成の例 :id=h-9556033567c4

```text
src/main/java/com/example/app/
  controller/
  service/
  repository/
  entity/
  dto/
  config/
src/main/resources/
  mapper/
  static/
  templates/
```

Java のパッケージ名は小文字にします。repository には DAO や Mapper インターフェースを置き、リソースの mapper ディレクトリには SQL のマッピングファイルを置きます。

Spring Boot の static は静的リソース、templates はテンプレートエンジンのファイルを置く場所です。Thymeleaf を追加しても、すべての静的ページが自動的に置き換わるわけではありません。JSP は配置方法が異なり、templates に置くだけで処理されるものではありません。

## サービスとインターフェースの境界 :id=h-608381cd367f

Controller は簡潔にしますが、検証と変換だけを行うわけではありません。HTTP ステータスコードやレスポンスヘッダーなど、表示層の処理も担当します。

Service は業務処理を担当します。すべてのテーブルに完全な CRUD が必要とは限らず、すべての Service に ServiceImpl が必要でもありません。実装の差し替え、テストの境界、チーム規約などの理由がある場合にインターフェースを導入します。

複雑な業務処理は複数のサービスに分け、コンストラクター注入で連携させられます。getXXXService().getRepository() のような呼び出しで、内部構造を段階的に公開しないでください。

| 操作     | メソッド名の例                 | 決めておく動作                      |
| ------ | ----------------------- | ---------------------------- |
| 作成     | createUser(request)     | 入力の検証、重複データの扱い               |
| 更新     | updateUser(id, request) | 対象が存在しない場合の動作                |
| 1 件を検索 | findUserById(id)        | Optional や null を返すか、例外を投げるか |
| 一覧を検索  | listUsers(query)        | 絞り込み、並べ替え、ページ分割              |
| 削除     | deleteUser(id)          | 対象が存在しない場合にエラーとするか           |

DDD の集約は、業務上の整合性を保つ境界を表すモデルです。多数の子 Service を持つ Service の別名ではありません。
